\section{Implementation \& Evaluation}\label{sec:evaluation}

Our prototype implementation of DSphinx, which we will release under an open-source license upon
publication of this paper, is available for review on Anonymous Github.\footnote{\url{\artifact}}
We have implemented DSphinx in Python 3.13 using the \emph{ECPy}\footnote{\url{https://pypi.org/project/ECPy/}} library for elliptic curve operations.
ECPy is well-suited for prototyping due to its simplicity, but it is significantly slower than many EC python libraries (approximately one order of magnitude slower). 
However, it is one of the few Python libraries that support Montgomery Curve25519, which is essential for Elligator.

We evaluate our implementation on two main axes: unlinkability and computational complexity.
The first one is empirically measured by evaluating output randomness, giving the raw resistance to correlation via advanced cryptanalysis techniques.
The second count the number of cryptographic operations which are the heaviest computations in the scheme.


\subsection{Unlinkability: Header Randomness}\label{sec:output_randomness}\label{sec:NIST}
To evaluate the statistical quality of our generated headers, we employ the NIST SP 800-22 statistical test suite~\cite{NIST-SP80022}.
This suite comprises 15 tests designed to assess whether a binary sequence exhibits properties expected from a truly random source.
Each test produces a \emph{p-value}, which measures how likely the data could be produced by a uniform source. 
If headers are truly random, the distribution of p-values over many samples should be statistically uniform.
Below we summarize the tests most relevant to our analysis:
\begin{itemize}
    \item \emph{Frequency Test}:
    Evaluates the balance between zeros and ones across the sequence. 
    A uniform random bitstring should contain roughly equal proportions of each.

    \item \emph{Matching Tests (Overlapping / Non-overlapping)}: 
    Examine how frequently predefined $n$-bit patterns (with default $n=9$) appear in the sequence.
    The non-overlapping version avoids reusing bits after a match, while the overlapping version slides the window by one bit at a time, capturing local repetition patterns.

    \item \emph{Random Walk Tests}:
    Interpret each bit as a step in a random walk ($+1$ for one, $-1$ for zero) and analyze its deviation from the expected mean behavior.
    The {cumulative sums} test checks how far the walk strays from zero.
    The {random excursions} and {random excursions variant} tests count how
    often specific states are visited, either per cycle (i.e., a segment of the
    walk between two successive zero states, i.e. states where the cumulative
    sum equals $0$) or across the entire sequence.
\end{itemize}
In short, while the \emph{Frequency} test verifies global balance, the \emph{Matching} tests detect hidden repetitive structures, and the \emph{Random Walk} tests analyze the dynamic balance of bits over time.

% \smallskip
We compare our decentralized implementation against the original Sphinx
implementation by Danezis\footnote{\url{https://github.com/UCL-InfoSec/sphinx}} using identical test suite configurations.

\noindent\textbf{Datasets Generation.}
%
Twenty independent datasets were generated for both implementation.
Each dataset was produced from a simulated network of 20 nodes and 3 semi-trusted third parties (STTPs).
For each epoch, a random destination IP and a path of three nodes were selected.
According to NIST requirements, each input sequence should contain at least $1\,000\,000$ bits.
We therefore concatenated multiple generated headers to reach a sequence of this size, repeating the process to obtain 100 sequences per dataset.

% \smallskip
NIST recommends interpreting results via two complementary criteria:
\begin{itemize}
    \item Proportion of passing sequences (Fig.~\ref{fig:proportion});
    \item Uniformity of p-value distributions (Figs.~\ref{fig:hist_p-values} and \ref{fig:chisquare}).
\end{itemize}

% \medskip
\noindent\textbf{Passing Rate Analysis.}
%
Fig.~\ref{fig:proportion} highlights the proportion of sequences that passed each NIST test for both implementations.
Following NIST guidelines, the significance level is set to $\alpha = 0.01$, and the confidence interval over $n$ samples is defined as:
$$
(1 - \alpha) \pm 3 \sqrt{\frac{\alpha (1 - \alpha)}{n}},
$$

Our implementation fails only three tests: \textit{Non-overlapping Matching}, \textit{Random Excursions}, and \textit{Random Excursions Variant}, all of which are also failed by the original Sphinx implementation.  
In contrast, DSphinx passes three tests that Sĥinx fails: \textit{Frequency}, \textit{Cumulative Sums}, and \textit{Overlapping Matching}.

% \medskip
\noindent\textbf{P-value Distribution Analysis.}
%
Fig.~\ref{fig:hist_p-values} shows the p-value histograms for both implementations across all 15 NIST tests.
Uniformity of these distributions is further assessed using a Chi-square goodness-of-fit test with a significance threshold of $0.0001$, as recommended by NIST.
Fig.~\ref{fig:chisquare} presents these results, highlighting that our implementation achieves uniform p-value distributions on the \textit{Frequency} and \textit{Cumulative Sums} tests, whereas the original Sphinx fails them.

\noindent\textbf{Discussion.}
%
In terms of output randomness, our decentralized implementation performs better than the original Sphinx, as it passes a greater number of statistical tests, as summarized in Table~\ref{tab:test_summary}.
The results suggest that both implementations may exhibit subtle patterns or hidden structure, as indicated by failures in the \textit{Random Excursions} and the \textit{Non-overlapping Matching} tests. 
This behavior could potentially come from the underlying mathematical framework (e.g. elliptic curves), which is not inherently truly random.
Nevertheless, our implementation demonstrates a better overall balance between ones and zeros, as reflected in the \textit{Frequency} and \textit{Cumulative Sums} test results.
Given the established security of the original Sphinx protocol, and considering the similarities in core structure, our results indicate that our scheme is a solid starting point toward achieving similar privacy guarantees.

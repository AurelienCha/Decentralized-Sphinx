\section{Empirical Results}\label{sec:evaluation}

% All experiments were conducted on a workstation running Arch Linux (x86\_64) equipped with an Intel Core i5-7400 processor clocked at 3.50 GHz, 8 GB of RAM.
% Several open-source mixnet implementations based on the \emph{Sphinx} packet format exist, notably Nym\footnote{\url{https://nym.com/docs/developers}} and Katzenpost\footnote{\url{https://github.com/katzenpost/katzenpost}}. 
% However, these systems incorporate numerous additional components and optimizations that make them unsuitable as direct baselines for evaluating the proposed \emph{DSphinx} design.
To ensure a meaningful comparison, both implementations were developed in Rust. 
The reference implementation relies on the existing \emph{sphinx-packet}\footnote{\url{https://lib.rs/crates/sphinx-packet}} library, while DSphinx is implemented as a dedicated Rust prototype. 
Although functional, the DSphinx implementation has not been optimized for performance.
Consequently, the reported measurements should be interpreted as preliminary results that characterize the current prototype rather than the performance of a fully optimized implementation.

Table~\ref{table:benchmark} reports latency and binary size measurements for both Sphinx and DSphinx with routes of three mixnodes.
Mixnode latency corresponds to the time required for a mixnode to process a single packet. 
Client latency denotes the time required to construct a complete packet, including STTPs latency. 
STTP latency represents the computation time of a single STTP during packet construction (these computations are performed in parallel).

The results show that DSphinx introduces a noticeable computational overhead compared with the original Sphinx construction. 
Mixnode processing latency increases from 0.15 ms to 2.23 ms, while client-side packet construction latency increases from 0.47 ms to 7.22 ms. 
Overall, the measured latency of DSphinx is approximately one order of magnitude higher (x15) than Sphinx. 
This increase is expected, as DSphinx requires additional cryptographic operations to support decentralized packet construction.

In DSphinx, packet processing at mixnodes is linear in the path length. During packet construction, STTP computations are quadratic in the path length, whereas client-side computations are linear in both the path length and the number of participating STTPs due to the distribution and aggregation of cryptographic material.
The scalability results reported in Table~\ref{table:benchmark} indicate that packet construction latency grows approximately linearly with the number of participating STTPs, which is consistent with the theoretical complexity. 

Overall, the evaluation highlights the trade-off introduced by DSphinx. 
Although DSphinx introduces a measurable computational overhead compared to Sphinx, the absolute increase remains modest in the context of a deployed mixnet. 
Recent measurements of the Nym mixnet report end-to-end latencies between approximately 500 ms and 800 ms, largely dominated by mixing delays (approximately 50 ms per hop) and network propagation rather than cryptographic processing \cite{diaz2024reliability}. 
In comparison, the additional packet-construction overhead introduced by DSphinx remains below 15 ms in all evaluated configurations. 
Consequently, this overhead is unlikely to dominate the overall end-to-end latency of a practical deployment.

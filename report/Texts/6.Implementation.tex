To evaluate the statistical quality of our DSphinx headers, we compare our implementation\todo{github link} 
against the original Sphinx implementation by Danezis\footnote{\url{https://github.com/UCL-InfoSec/sphinx}}, using 
the NIST SP 800-22 statistical test suite~\cite{NIST-SP80022} with identical configurations.
This suite comprises 15 tests designed to assess whether a binary sequence exhibits properties expected from a truly random source.
Each test produces a p-value, which measures how likely the data could be generated by a uniform source. 
If headers are truly random, the distribution of p-values over many samples should be statistically uniform.
NIST recommends interpreting results via two complementary criteria;
(i) the proportion of passing sequences,
and (ii) the uniformity of p-value distributions.
Below we summarize the tests most relevant to our analysis.
\begin{itemize}
    \item \textbf{Frequency test}:
    Measures the balance between zeros and ones.  
    A uniform random bitstring should contain roughly equal proportions of each.

    \item \textbf{Matching tests}: 
    Count how often predefined $n$-bit patterns appear.% (default $n=9$)
    The non-overlapping version does not reuse bits after a match, while the overlapping version slides the window by one bit, capturing local repetitions.

    \item \textbf{Random Walk tests}:
    Treat each bit as a step in a random walk ($+1$ for one, $-1$ for zero) and analyze deviations from the expected behavior.  
    The \emph{cumulative sums} test checks the distance of the walk from zero.  
    The \emph{random excursions} tests count how often specific states are visited, either per cycle (i.e. between successive zero states), or over the entire sequence.
\end{itemize}
In short, the \emph{frequency} test checks global balance, the \emph{matching} tests detect hidden repetitive patterns, and the \emph{random walk} tests assess the dynamic balance of bits over time.

\medskip
\noindent\textbf{Dataset Generation.}
Twenty independent datasets were generated for both implementation.
Each dataset was produced from a simulated network of 20 nodes and 3 semi-trusted third parties (STTPs).
For each epoch, a random destination IP and a path of three nodes were selected.
According to NIST requirements, each input sequence should contain at least $1\,000\,000$ bits.
We therefore concatenated multiple generated headers to reach a sequence of this size, repeating the process to obtain 100 sequences per dataset.

\medskip
\noindent\textbf{Results Analysis.}
The results for both, our DSphinx implementation and the original Sphinx, are summarized in Table~\ref{tab:test_summary}.
In terms of output randomness, our decentralized implementation performs better than the original Sphinx, as it passes a greater number of statistical tests.
The results suggest that both implementations may exhibit subtle patterns or hidden structure, as indicated by failures in the \textit{Random Excursions} and the \textit{Non-overlapping Matching} tests. 
This behavior could potentially come from the underlying mathematical framework (e.g. elliptic curves), which is not inherently truly random.
Nevertheless, our implementation demonstrates a better overall balance between ones and zeros, as reflected in the \textit{Frequency} and \textit{Cumulative Sums} test results.
Given the established security of the original Sphinx protocol, and considering the similarities in core structure, our results indicate that our scheme is a solid starting point toward achieving similar privacy guarantees.

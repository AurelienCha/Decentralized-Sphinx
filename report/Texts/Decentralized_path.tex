
\subsection{Decentralized Path Selection}
\label{sec:distrib-path}
In this section, we present a proof-of-concept approach for decentralizing path selection. This is particularly important to prevent attacks by malicious clients, such as biased routing~\cite{benguirat2022mixnet} and $(N-1)$ attacks~\cite{wright03}. This preprocessing phase, which can be integrated with DSphinx as illustrated as new steps \emph{(0)} to \emph{(3)} in Fig.~\ref{fig:overview_with_decentralized_path}, may be designed differently depending on the underlying network (e.g. mixnets or the Lightning Network), and on system configuration, such as whether IP addresses are published on the blockchain or in a centralized server. While our main contribution is the core protocol, this section provides intuition on how such a preprocessing phase could be incorporated. In general, any mechanism that replaces the client’s computation of secret shares in Section~\ref{sec:scheme}, with a decentralized scheme can be integrated with our protocol.

In order to prevent attacks such as biased routing~\cite{benguirat2022mixnet} and $(N-1)$ attacks~\cite{wright03}, the protocol should be coupled with a mechanism whereby the routing path is selected by the STTPs rather than by the client.
\subsubsection{Overview}

Each mixnode's private key $k_i$ is distributed among STTPs using Shamir Secret Sharing, resulting in a distributed symmetric key shared among the STTPs.
Consequently, the client cannot derive routing secrets independently and must query a set of STTPs to obtain partial cryptographic material for the shared secrets associated with a pseudorandomly selected path.

Upon receiving a nonce from the client, the STTPs pseudorandomly sample a path and return shares of the corresponding secret materials. 
After collecting a threshold number of responses, the client reconstructs the shared secrets and proceeds with the DSphinx header construction (Fig.~\ref{fig:overall_schema}).

\subsubsection{Setup.}

\end{comment}

Each STTP $t$ is identified by a value $ID_t = H(IP_t)$, where $IP_t$ denotes the IP address of the STTP. 
Each mixnode $i$ samples a random identifier $r_i$ and constructs two random polynomials $f_i$ and $g_i$ of degree $n-1$ respectively satisfying the constraint $f_i(0) = k_i$, and $g_i(0) = N_i$. 
Here, $k_i$ denotes the mixnode's secret key, $N_i$ its address point, and $n$ the reconstruction threshold of the Shamir sharing scheme. The mixnode then distributes to each STTP $t$ the share defined in Eq.~\ref{eq:sttp_share}. 
These shares are delivered anonymously so that STTPs cannot associate them with specific mixnodes.
STTPs store these shares indexed by the identifier $r_i$, which later serves to pseudorandomly select mixnodes during path sampling.
\begin{equation}
    (r_i,\quad k_{i_t}=f_i(ID_t),\quad N_{i_t}=g_i(ID_t))
    \label{eq:sttp_share}
\end{equation}

Adding a new mixnode only requires executing the setup procedure for that node. Adding a new STTP requires each mixnode to generate and transmit an additional share. 
If the threshold parameter $n$ changes, however, the entire setup procedure must be repeated.

\subsubsection{Path Selection.}

To sample a routing path, the client sends a nonce $w$, which serves as a randomness seed, to a set of $n$ STTPs. Each STTP first computes the elliptic curve point $\A{} = \Map(w)$, where $\Map(\cdot)$ denotes the Elligator mapping. This mapping produces a uniformly distributed elliptic curve point whose discrete logarithm relative to the base point $G$ is unknown.

For each hop position $i$, the STTP selects the mixnode share $(r_i, k_{i_t}, N_{i_t})$ whose identifier $r_i$ is closest to $H(w \parallel \text{timestamp} \parallel i)$.
Then it computes a share of the Diffie-Hellman value associated with the selected mixnode shares as $S_{i_t} = k_{i_t} \A{}$,
and returns to the client the tuple $(ID_t,\, N_{i_t},\, S_{i_t})$.

\subsubsection{Secret Reconstruction.} 

Upon receiving responses from a threshold number of STTPs, the client reconstructs the mixnode address points and shared secret points using Lagrange interpolation, as shown in Eq.~\ref{eq:lagrange_reconstruction}. 
Here, $\lambda(ID_t)$ denotes the Lagrange interpolation coefficient associated with STTP identifier $ID_t$. 
Since the same nonce $w$ is used by all STTPs, the reconstructed points correspond to the same sequence of mixnodes selected during the path sampling phase.
\begin{equation}
    N_i = \sum_t \lambda(ID_t) N_{i_t}, \qquad
    S_i = \sum_t \lambda(ID_t) S_{i_t},
    \label{eq:lagrange_reconstruction}
\end{equation}

To prevent linkability, the client samples a random scalar $r$ and rerandomizes the shared secrets by computing $S'_i = r S_i$. 
The corresponding cryptographic header element is updated accordingly as $\A{}' = r\A{}$.

Since DSphinx derives shared secrets sequentially, the client computes the scalar shared secrets in cascade. 
For each hop $i$, the corresponding scalar secret is obtained by combining the reconstructed point with the secrets of the previous hops and mapping the result back to the scalar field, as shown in Eq.~\ref{eq:cascade_secret}. 
\begin{equation}
    s'_i = \Map^{-1}\!\left(S'_i \prod_{j=1}^{i-1} s'_j \right).
    \label{eq:cascade_secret}
\end{equation}

Finally, the client proceeds with the standard DSphinx header construction protocol (Section~\ref{sec:scheme}) using $\A{}'$, together with the reconstructed values $N_i$ and $s'_i$ for each hop $i$ along the path.

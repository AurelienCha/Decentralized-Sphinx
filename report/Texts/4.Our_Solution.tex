\section{DSphinx Packet Format}

% Header structure - Chunks
DSphinx is inspired by the Sphinx packet format, with the key distinction that each header element is independently encoded as an elliptic curve (EC) point. 
Consequently, the DSphinx header is structured as a sequence of fixed-size chunks, as illustrated in Fig.~\ref{fig:chunkwise-overview}, where each chunk corresponds to a single header element represented by an EC point.
Each network node along the packet route contributes two chunks: one encoding its address and another encoding a per-hop integrity tag. 
Therefore, a route of length $m$ is represented by $n = 2m + 1$ chunks, accounting for two chunks per network node and one additional chunk corresponding to the final destination.

\subsection{Chunk Generators}

% Independent Generator for each chunk
To preserve the security properties discussed in Section~\ref{sec:indep_generators}, each chunk is associated with a distinct generator. 
We define a set of generators $\{G_j\}_{j=1}^{n}$, where each generator corresponds to a specific chunk position.
These generators must be \emph{independent}, meaning that the scalar relationship between any pair of generators is unknown, as is their discrete logarithm with respect to the curve base point $G$. 
Formally, there exists no efficiently computable $z_j \in \mathbb{Z}_p$ such that $G_j = z_j G$.
To instantiate such generators, DSphinx derives them using the Elligator mapping~\cite{bernstein2013elligator}.
The resulting points are computationally indistinguishable from randomly sampled curve points, thereby preventing any known scalar relationship between generators.

% Formula + Refresh
To maintain long-term security and limit the lifetime of public parameters, all participating entities (clients, network nodes, and STTPs) periodically refresh the set of chunk generators. 
To ensure consistent generator derivation across all entities, generators are deterministically derived from a common seed obtained by hashing the current timestamp truncated to a predefined refresh interval. 
An offset $j$ is then used to derive a distinct generator for each chunk, as shown in ~\eqref{eq:chunk_generators}, where $\Map{\cdot}$ denotes the Elligator mapping and the factor $8$ corresponds to the curve cofactor.
\begin{equation}
    G_j = 8 \cdot \Map{\hash{\text{timestamp}} + j}
    \label{eq:chunk_generators}
\end{equation}

\subsection{Elligator}

% Elligator
Representing IP addresses as elliptic curve points requires a reversible encoding between integers and curve points.
Classical encodings typically map an integer to the $x$-coordinate of a valid curve point.
However, such approaches succeed only for approximately half of all inputs and may introduce structural bias.
To overcome these limitations, we employ Elligator~\cite{bernstein2013elligator}, which provides a deterministic mapping from integers to curve points while producing outputs that are uniformly distributed and computationally indistinguishable from randomly sampled points. 
We denote the Elligator mapping $\Map{\cdot} : \mathbb{Z}_p \rightarrow \mathbb{G}$ and its inverse $\InverseMap{\cdot} : \mathbb{G} \rightarrow \mathbb{Z}_p$.

% Clearing cofactor
Since Elligator may output points outside the prime-order subgroup generated by $G$, the resulting point must be multiplied by the curve cofactor (equal to 8 for Curve25519). 
This operation, commonly referred as \emph{cofactor clearing}, ensures that all derived points belong to the prime-order subgroup. 
Doing so prevents small-subgroup attacks, which could otherwise leak a few bits of information through computations involving points of small order.


\section{Protocol Description}\label{sec:scheme}

% Overview
The proposed decentralized protocol distributes the Sphinx header construction across multiple semi-trusted third parties (STTPs). 
More precisely, it decentralized the path selection to a set of semi-trusted third parties to prevent bias route.
Fig.~\ref{fig:overall_schema} illustrates the protocol which can be diveded in three phases; (i) a one-time setup phase (step 0),  
(ii) a decentralized path sampling phase (step 1-3), and (iii) the header construction (step 4).

\subsection{Setup} % The goal of the setup phase is to distribute shares of each network node's secret key and routing information among the STTPs.

Each network node $i$ samples a random identifier $r_i$ and constructs two random polynomials $f_i$ and $g_i$ of degree $d-1$, such that:
$f_i(0) = k_i$ and $g_i(0) = N_i$, where $k_i$ denotes the node's secret key, $N_i \in \mathbb{G}$ its encoded address, and $d$ the reconstruction threshold.

Each STTP is identified by a value $t$, computed as the hash of its address. 
For each STTP $t$, network node $i$ evaluates $f_i(t)$ and $g_i(t)$ and securely transmits the corresponding shares together with $r_i$ to the STTP $t$ as in \eqref{eq:sttp_share}.
We assume these shares are transmitted anonymously, preventing STTPs from linking them to specific nodes. 
Each STTP stores the received shares indexed by $r_i$, which later serves to pseudorandomly select network nodes during path sampling.
\begin{equation}
    (r_i,\quad k_{it}=f_i(t),\quad N_{it}=g_i(t))
    \label{eq:sttp_share}
\end{equation}

Adding a new node only requires executing the setup procedure for that node. 
Adding a new STTP requires each node to compute and distribute an additional polynomial evaluation. 
However, changing the threshold $d$ requires reinitializing the entire setup.


\subsection{Path Sampling}\label{sec:path_sampling}

To sample a routing path, the client sends a nonce $w$, used as a randomness seed, to a set of at least $d$ STTPs. 
Each STTP maps the nonce to an elliptic-curve point ($\A{} = HashToCurve(w)$) using a proper hash-to-curve function (i.e non-reversible, see section \ref{sec:hash-to-curve}). 
The resulting point acts as a cryptographically randomness source, where recovering its discrete logarithm is assumed infeasible, preventing manipulation of the sampling process.

For each hop $i$, the STTP computes an index $r'_i = hash(\A{}, \text{timestamp}, i)$,
which binds the selection to the client nonce, time, and hop position, preventing replay.
The STTP then selects the stored share $(r_i, k_{it}, N_{it})$ whose identifier $r_i$ is closest to $r'_i$, and computes a partial Diffie-Hellman shared secret as $S_{it} = k_{it} \A{}$.
Finally, it returns $(t, N_{it}, S_{it})$ to the client.

\subsection{Aggregation}

Upon receiving responses from at least $d$ STTPs, the client reconstructs node addresses and shared secrets via Lagrange interpolation:
\begin{equation}
    N_i = \sum_t \lambda(t) N_{it}, \qquad
    S_i = \sum_t \lambda(t) S_{it},
    \label{eq:lagrange_reconstruction}
\end{equation}
where $\lambda(t)$ denotes the Lagrange coefficient associated with STTP identifier $t$.
Since all STTPs process the same nonce $w$, the reconstructed values correspond to a consistent path.

To prevent linkability, the client samples a random scalar $r$ to rerandomizes the shared secrets, and updates accordingly the cryptographic element $\A{}$.
The final per-hop shared secrets are derived iteratively in a cascade, where each hop incorporates previous shared secrets:
\begin{equation}
    s_i = \InverseMapNoParenthesis \!\left(r S_i \prod_{j=1}^{i-1} s_j \right).
    \label{eq:cascade_secret}
\end{equation}


\subsection{Header Construction}
Given the reconstructed route $\{N_i\}_{i=1}^{m}$ and per-hop shared secrets $\{s_i\}_{i=1}^{m}$, the client constructs the DSphinx header for destination $\D{}$ (encoded in $\mathbb{G}$).
The header construction proceeds in two phases; 
a preprocessing phase (Alg.~\ref{algo:preprocessing}, Fig.~\ref{fig:chunk-preprocessing}) that generates filler chunks, 
followed by a layer-by-layer encryption phase (Alg.~\ref{algo:sttp}, Fig.~\ref{fig:chunk-encryption}) applied in reverse order, from the last hop to the first.

% Preprocessing
\smallskip
\noindent\textbf{Preprocessing Phase.}
The preprocessing phase prepares a vector of filler chunks $\phi$ according to \eqref{eq:preprocessing}.
These filler chunks ensure that after each encryption layer the last two chunks evaluate to the identity element and can thus be safely truncated, ensuring a constant header size and reversibility when processed by the network nodes. 
The detailed procedure is specified in Alg.~\ref{algo:preprocessing}, which takes as input the set of shared secrets $\{s_i\}$ and the set of chunk generators $\{G_j\}$, and outputs $n-1$ filler chunks, where $n = 2m+1$ is the header size for a path of length $m$. 
An example for $m=3$ is illustrated in Fig.~\ref{fig:chunk-preprocessing}.
\begin{equation}
    \phi_j = - \sum_{i=1}^{m} s_i\, G_{\,n+j-2i}, \qquad 1 \le j \le n-1 .
\label{eq:preprocessing}
\end{equation}

% Layers
\noindent{\textbf{Layered Encryption Phase.}}
The header is initialized by concatenating the destination chunk $\D{}$ with the filler chunks $\phi$, producing a $n$-chunks header.
Encryption is then applied iteratively in reverse path order, from $i=m$ down to $i=1$, 
as illustrated in Fig.~\ref{fig:chunk-encryption} and detailed in Alg.~\ref{algo:sttp}.
\begin{enumerate}
    \item \textbf{Chunk encryption:}: 
    Each chunk $j$ is encrypted according Eq.~\eqref{eq:layer_i}.
    The last two chunks evaluate to the identity element as a consequence of the preprocessing phase and may therefore be discarded while preserving subsequent processing.
    \begin{equation}
        H_{ij} = H_{(i+1,\,j)} + \sG{i}{j}
        \label{eq:layer_i}
    \end{equation}

    \item \textbf{Integrity computation:} 
    The remaining chunks are used to compute an HMAC as integrity tag:
    \begin{equation}
        \C{i} =  \text{HMAC}(\B{i}{}, s_i)
        \label{eq:integrity}
    \end{equation}

    \item \textbf{Prepend Node:}
    The node address $\N{i}$ and the integrity tag $\C{i}$ are prepended to $H_i$, producing again a $n$-chunks header.
\end{enumerate}

\subsection{Network Nodes Processing}
Upon receiving a packet, node $i$ extracts the cryptographic element $\A{i}$, the integrity tag $\C{i}$, and the encrypted routing information $\B{i}{}$. 
As in the original Sphinx design, the node checks whether $\A{i}$ has been previously observed since its last key rotation and discards duplicates to prevent replay attacks.

The header is processed as illustrated in Fig.~\ref{fig:chunk-decryption}.
The node first derives the shared secret $\s{i}$ by multiplying the cryptographic element $\A{i}$ with its private key $\sk{i}$, and then applied the inverse Elligator mapping as in \eqref{eq:derive_secret}.
\begin{equation}
\begin{aligned}
    \s{i} &= \InverseMap{(\sk{i} \, \A{i})}
\end{aligned}
\label{eq:derive_secret}
\end{equation}

% Integrity verification
\noindent
The shared secret $\s{i}$ is then used to verify the integrity tag in \eqref{eq:integrity_check}. 
\begin{equation}
\C{i} \overset{\text{?}}{=} \text{HMAC}(\B{i}{}, \s{i})
\label{eq:integrity_check}
\end{equation}

% Decryption
If verification succeeds, the node appends two identity chunks to the header and decrypts it as \eqref{eq:decrypt}.
\begin{equation}
\BB{i}{j} = \B{i}{j} - \sG{i}{j}
\label{eq:decrypt}
\end{equation}
The first decrypted chunk $\BB{i}{1}$ reveals the next hop $\N{i+1}$. 
The second chunk $\BB{i}{2}$ contains the integrity tag $\C{i+1}$ for the next hop, 
while the remaining chunks form the next encrypted routing information $\B{i+1}{}$.

% Update Alpha
Finally, the node updates the cryptographic element according to \eqref{eq:update_alpha}
and forwards the packet with header $(\A{i+1},\, \B{i+1}{},\, \C{i+1})$ to the next hop.
\begin{equation}
\A{i+1} = s_i \, \A{i}
\label{eq:update_alpha}
\end{equation}
% The shared secret $s_i$ acts as a per-hop pseudorandom update that derives the next blinding factor, ensuring that the cryptographic elements $\A{i}$ remain unlinkable across layers.

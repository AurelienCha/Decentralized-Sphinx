\section{Protocol description}\label{sec:scheme}

% Overview
The proposed decentralized protocol distributes the header construction across multiple semi-trusted third parties (STTPs). 
Figure~\ref{fig:overall_schema} illustrates the protocol in five steps.
(1) The client randomly selects a route and a secret nonce $x$, from which he derives a sequence of shared secrets.
Each shared secret is split into $t$ additive shares, alongside the IP addresses of the nodes and the final destination.
(2) Each set of shares is sent to $t$ different STTP, along with the necessary cryptographic elements.  
(3) Each STTP independently computes a \textit{partial} Sphinx header using its shares.  
(4) The client then aggregates these partial headers to reconstruct the final header. 
(5) Finally, the client encrypts the payload accordingly to the header and sends the message through the decentralized network.

% Header structure - Chunks
In our decentralized Sphinx header construction, each piece of header information is represented as an elliptic curve (EC) point.
The header is thus divided into fixed-size chunks, as illustrated in Figure~\ref{fig:chunked_schema}, where each chunk corresponds to one EC point.
Each node along the path adds two chunks: one encoding its IP address and another representing its integrity tag.
Without loss of generality, we consider paths of three nodes in this paper, resulting in a seven-chunks header (i.e. seven EC points), two per node plus one additional chunk for the final destination's IP address.

% Elligator
Representing IP addresses as elliptic curve points requires a reversible mapping between integers and curve points.  
We define a mapping $\Map{}$ from integers to points and its inverse $\InverseMap{}$ such that $\InverseMap{\Map{x}} = x$ for any integer $x$.  
Classical encodings map an integer directly to the $x$-coordinate of a valid point, but it succeeds only for roughly half of integers and introduces structural bias. 
To avoid this issue, we rely on the Elligator mapping~\cite{bernstein2013elligator}, which deterministically maps any integer to a curve point while ensuring that the resulting points are uniformly distributed and computationally indistinguishable from randomly sampled points.  
This property allows IP addresses to blend seamlessly with other cryptographic elements of the Sphinx header.
\newline

In summary, the protocol is organized into four main components, each described in the following subsections:
\begin{itemize}
    \item \textbf{Setup:} generation of independent random generators;
    \item \textbf{Client:} additive sharing of information to STTPs;
    \item \textbf{STTP:} encryption of shares into partial headers;
    \item \textbf{Network Nodes:} decryption and forwarding of packets.
\end{itemize}

\subsection{Setup}

As discussed in Section~\ref{sec:indep_generators}, each chunk requires a distinct generator to preserve the scheme's security properties. 
We therefore define a set of seven generators $\{G_j\}$, one for each chunk $j$.

% Synchronization
In principle, the setup phase can be executed only once. 
However, to maintain security over time, the set of generators should be refreshed periodically. 
All entities (clients, nodes, and STTPs) must perform the setup phase to ensure synchronization of generators. 
To achieve synchronization, generators are derived from a common seed computed as the hash of the current timestamp, truncated to the chosen refresh interval, and incremented to differentiate generators.

% Independent
To preserve the scheme's security properties, the generators must be \emph{independent}, meaning that the scalar relationship between any two generators is unknown. 
Formally, no entity should know any $z_j \in \mathbb{Z}_N$ such that $G_j = z_j G$, where $G$ is the curve's base point. 
This property is guaranteed by using the Elligator mapping~\cite{bernstein2013elligator}, which provides a uniform and pseudorandom mapping while ensuring that each $G_j$ is computationally \emph{independent} from $G$ and from the other generators.

% Clearing cofactor
A subtlety with Elligator is that it may map integers to points on the full curve group, not exclusively within the large prime-order subgroup (i.e. the subgroup generated by $G$). 
This could enable a \emph{small subgroup attack}, potentially leaking up to 3 bits of information. 
This can be prevented by \emph{clearing the cofactor}, i.e. each generator is multiplied by the curve's cofactor (8 for Curve25519) to ensure it lies in the prime-order subgroup.

% Formula
The resulting formula for the $j^{th}$ generator is therefore:
\begin{equation}
G_j = 8 \cdot \Map{\hash{\text{timestamp}} + j}.
\end{equation}


\subsection{Client}

To send a message to a chosen destination, the client first selects a random path through the network and generates an initial nonce.  
Using this nonce and the public keys of the nodes along the path, the client derives a sequence of shared secrets \((\s{1}, \s{2}, \s{3})\)
according to Eq.~\ref{eq:shared_secret}, yielding a hop-by-hop key derivation.
\begin{equation}
(\s{1}, \s{2}, \s{3}) \quad \left\{ \quad
\begin{aligned}
    \A{i}    &= x_i \, G, \\
    \s{i}    &= \InverseMap{x_i \, \PK{i}}, \\
    x_{i+1}  &= s_i \, x_i \quad (\text{mod}\ n),
\end{aligned}
\right.
\label{eq:shared_secret}
\end{equation}
where $x_1$ is the client's nonce, $\PK{i} = \sk{i}\,\G{}$ is the public key of the $i^{th}$ node, $n$ is the large prime subgroup order (i.e. $(n+1)\G{} = \G{}$), and $\InverseMap{}$ is the inverse Elligator, mapping EC point to integer.
The scalar $s_i$ provides as a per-hop pseudorandom update, ensuring that the cryptographic element $\A{i}$ remain unlinkable across layers.

Next, the client encodes the routing information for each hop
IP addresses are padded with random bits and mapped to elliptic curve points via Elligator, ensuring that each address can later be recovered while appearing indistinguishable from a random point.  
Both these IP points and the derived shared secrets are then additively split into $t$ shares.  
Each STTP receives one share of every value, together with the hash of derived shared secrets.

Each STTP independently processes its assigned shares and returns a \emph{partial} header to the client.  
The client aggregates these partial headers by performing chunk-wise elliptic-curve point additions, thereby reconstructing the complete encrypted DSphinx header.
Once aggregation is complete, the client attaches $\A{1}$ and sends the finalized header, together with the encrypted payload, to the first node on the path.


\subsection{Semi-Trusted Third Party}


Each semi-trusted third party (STTP) receives from the client only a subset of the information required to construct the full DSphinx header.
It obtains a share of the destination address (EC point $\Delta$), and for every node along the path:
\begin{itemize}
    \item a share of its address (EC points $\N{i}$);
    \item a share of its shared secret (scalars $\s{i}$);
    \item the hash of its shared secret (scalars $\sHashed{i}$).
\end{itemize}
Using these shares, each STTP independently constructs a \emph{partial} encrypted header.  
As illustrated in Figure~\ref{fig:chunked_schema}, the computation proceeds in two stages: (i) a preprocessing phase that generates filler chunks, and (ii) a layer-by-layer encryption phase applied in reverse order, from the last hop to the first.
\newline

% Preprocessing
\noindent{\textbf{Preprocessing Phase.}}
The preprocessing step prepares a vector of filler chunks $\phi$ whose role is to cancel out during the encryption of successive layers, thereby ensuring a constant header size and enabling reversibility at the nodes. 
Algorithm~\ref{algo:preprocessing} takes as input the share of the shared secrets ${s_i}$ and the generators ${G_j}$ associated with each chunk $j$, and outputs $n-1$ filler chunks, where $n = 2m+1$ is the header size for a path of length $m$.
These filler chunks are given by (\ref{eq:preprocessing}) as illustrated in Figure~\ref{fig:chunked_schema} for the case where $m=3$.
These filler chunks are computed according to (\ref{eq:preprocessing}), and their structure for the case $m=3$ is illustrated in Figure~\ref{fig:chunked_schema}.

% Layers
\noindent{\textbf{Layered Encryption Phase.}}
After preprocessing, the STTP initializes the header by appending the destination share with the filler chunks, yielding a header of $n$ chunks.
Then, proceeding from hop $i = m$ down to $i = 1$, the STTP performs the following operations (Alg.~\ref{algo:sttp}):
\begin{enumerate}
    \item \textbf{Encrypt each chunk}: 
    Every chunk $j$ is encrypted with $\sG{i}{j}$ as:
    \begin{equation}
    H_{ij} = H_{(i+1,j)} + \sG{i}{j}.
    \label{eq:layer_i}
    \end{equation}
    Thus last two chunks whose result in identity elements and are safely removed.
    \item \textbf{Compute the integrity tag:} 
    The remaining chunks $\B{i}{1},\ldots,\B{i}{n-2}$ are used to compute the integrity tag as:% (\ref{eq:integrity}):
    \begin{equation}
        \C{i} = \sG{i}{} + \sum_{j=1}^{n-2} \big( \hashIt{\sHashed{i}}{j} \, \B{i}{j} \big)
        \label{eq:integrity}
    \end{equation}

% Integrity
\noindent{\textbf{Integrity Mechanism.}}
The integrity construction in \eqref{eq:integrity} combines two essential components:
\begin{itemize}
\item a \emph{pseudorandom weighted sum} where weights are derived from $\sigma_i$ through iterated hashing;
\item a \emph{blinding offset} term $s_i G$, ensuring that integrity tags remain unlinkable to STTPs that know the weights.
\end{itemize}
The pseudorandom weights prevent adversaries from introducing compensating modifications across chunks that preserve the checksum.
The blinding offset prevents STTPs from using their knowledge of the weights to correlate integrity tags across packets.
This design preserves homomorphism while ensuring unlinkability and integrity in the presence of partially corrupted STTPs.

% To preserve unlinkability, it is essential that the generators $ (\G{1}, \dots, \G{7}) $ are \textit{independent}, meaning their scalar relationships are unknown and computationally infeasible to derive.
% If the same generator \G{} were used across chunks (or their scalar relationships known), an adversary could compute chunk-wise difference between consecutive layers: $ \B{i}{j} - \B{i+1}{j} = \sG{i}{} $.
% Since the shared secret \s{i} remains consistent within a layer, the resulting differences would reveal a predictable pattern (uniform or preserved scalar relationships).
% This consistency could allow an adversary to correlate incoming and outgoing packets at a mixnode, thereby breaking the unlinkability property.
% Using independent generators for each chunk prevents such correlations and is therefore critical to the protocol's security.  


\subsection{Network Nodes}
Upon receiving a packet, node $i$ extracts the cryptographic element $\A{i}$, the integrity tag $\C{i}$, and the encrypted header chunks $\B{i}{}$.  
As in the original Sphinx design, the node stores previously seen $\A{i}$ values (until its private key is rotated).
If the received $\A{i}$ matches a stored value, the packet is discarded to prevent replay attacks.  
If the value is fresh, the packet is processed as illustrated in Figure~\ref{fig:mixnode_decryption}.

The node first reconstructs its shared secret point $\S{i}$ using its private key \sk{i}, and then maps this point to the corresponding shared integer $\s{i}$ using the Elligator inverse mapping:
\begin{equation}
\begin{aligned}
    \S{i} &= \sk{i} \, \A{i} \\
    \s{i} &= \InverseMap{\S{i}}\\
\end{aligned}
\label{eq:derive_secret}
\end{equation}

% Integrity verification
\noindent
This value $\s{i}$ is then used to verify the integrity tag:
\begin{equation}
\C{i} \overset{\text{?}}{=} \sG{i}{} + \sum_{j=1}^{5} \big( \hashIt{\s{i}}{j} \, \B{i}{j} \big)
\label{eq:integrity_check}
\end{equation}

% Decryption
If this check fails, the packet is discarded.
Otherwise, the node pads the header by appending two \textit{identity} chunks (i.e. point at infinity) and then updates it as:
\begin{equation}
{\BB{i}{j}} = \B{i}{j} - \sG{i}{j} \qquad \forall j = 1, \dots, 7
\label{eq:decrypt}
\end{equation}

The first resulting chunk, $\BB{i}{1}$, encodes the next node's IP address address (\N{i+1}).  
It is mapped back to an integer using the inverse Elligator map, after which the padding bits are removed.

The second chunk, $\BB{i}{2}$, becomes the integrity tag for the next hop ($\C{i+1}$).  
The remaining five chunks constitute the next encrypted routing information $(\B{i+1}{})$.

% Update Alpha
As specified in Eq.~\ref{eq:shared_secret}, the node applies the same update rule as the client to compute the next cryptographic element $\A{i+1}$:
\begin{equation}
\A{i+1} = s_i \, \A{i}
\label{eq:update_alpha}
\end{equation}
Finally, the node forwards the updated header $(\A{i+1}, \C{i+1}, \B{i+1}{})$ to the next node in the path.

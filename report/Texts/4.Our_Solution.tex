\section{Protocol Description}\label{sec:scheme}

% Overview
The proposed decentralized protocol distributes the Sphinx header construction across multiple semi-trusted third parties (STTPs). 
Fig.~\ref{fig:overall_schema} illustrates the protocol in four steps: (1) The client sends $t$ secret shares, representing the path of the packet, to $t$ different STTP, along with the necessary cryptographic elements.
(2) Each STTP independently computes a partial Sphinx header using its shares.  
(3) The client then aggregates these partial headers to reconstruct the final header. 
(4) Finally, the client encrypts the payload accordingly and sends the message through the decentralized network. Note that, for simplicity, we assume for this section that the client derives the secret shares (and thus chooses the path). However, to decentralize path selection, a scheme is required in which the STTP obtains these shares during a setup phase. 
The exact mechanism will depend on the particular system design and threat model. Nevertheless, we present a proof-of-concept construction for such a scheme in Section~\ref{sec:distrib-path}.

% Header structure - Chunks
In DSphinx, each header element is represented as an elliptic curve (EC) point. 
Accordingly, the header is divided into fixed-size chunks, as illustrated in Fig.~\ref{fig:chunkwise-overview}, with each chunk corresponding to a single EC point. 
Every network node along the path contributes for two chunks: one encoding its IP address and another representing its integrity tag. 
Thus, a path of length $m$ is represented by $n = 2m + 1$ chunks, accounting for two chunks per node and an additional chunk for the final destination. 

% Elligator
Representing IP addresses as elliptic curve points requires a reversible mapping between integers and curve points.  
We define a mapping $\Map{}$ from integers to points and its inverse $\InverseMap{}$ such that $\InverseMap{(\Map{(x)})} = x$ for any integer $x$.  
Classical encodings map an integer directly to the $x$-coordinate of a valid point, but it succeeds only for roughly half of integers and introduces structural bias. 
To avoid this issue, we rely on the Elligator mapping~\cite{bernstein2013elligator}, which deterministically maps any integer to a curve point while ensuring that the resulting points are uniformly distributed and computationally indistinguishable from randomly sampled points.  
This property allows IP addresses to blend seamlessly with other cryptographic elements of the Sphinx header.

\subsection{Setup}

% 1 Generator by chunk + Refresh 
Each chunk requires a distinct generator to preserve the scheme's security properties (Section~\ref{sec:indep_generators}). 
Accordingly, we define a set of $n$ generators $\{G_j\}_{j=1..n}$, one per chunk.
Although the setup phase could be executed only once, maintaining long-term security requires periodically refreshing the generators. 
All entities (clients, nodes, and STTPs) therefore run the setup phase to remain synchronized. 
Synchronization is achieved by deriving all generators from a common seed computed as the hash of the current timestamp, truncated to the refresh interval, with an offset used to differentiate generators.

% Independent
To preserve the scheme's security properties, generators must be \emph{independent}, meaning that the scalar relationship between any two generators is unknown. 
Formally, no entity should know any $z_j \in \mathbb{Z}_p$ such that $G_j = z_j G$, where $G$ is the curve's base point. 
This property is guaranteed by using the Elligator mapping~\cite{bernstein2013elligator}, which provides a uniform and pseudorandom mapping while ensuring that each $G_j$ is computationally \emph{independent} from $G$ or other generators.

% Clearing cofactor
Since Elligator may map output points on the full curve group instead of the large prime-order subgroup (i.e. the subgroup generated by $G$), 
it needs to be multiplied by the curve's cofactor (8 for Curve25519) to ensure it lies in the prime-order subgroup.
This procedure of \emph{clearing the cofactor} prevents \emph{small subgroup attack} that would leak a few bits of information (3 bits for Curve25519).

% Formula
Generators are therefore defined as $ G_j = 8 \cdot \Map{(\hash{\text{timestamp}} + j)} $.


\subsection{Client}
To send a message to a chosen destination, the client selects a routing path and generates an initial nonce.  
Using this nonce and the public keys of the nodes along the route, the client derives a sequence of hop-by-hop shared secrets $(s_1, s_2, s_3)$ according to Eq.~\eqref{eq:shared_secret}. 
As mentioned earlier, we assume for now that the client executes this part of the protocol. However, depending on the system design, the STTPs should instead receive these shares during a setup phase, as explained in Section~\ref{sec:distrib-path}.


Here, $x_1$ denotes the initial nonce, $\PK{i} = \sk{i} G$ is the public key of the $i^{\text{th}}$ node in the path, $p$ is the order of the prime subgroup, and $\InverseMap(\cdot)$ denotes the inverse Elligator mapping from elliptic curve points to scalars.
The shared secret $s_i$ acts as a per-hop pseudorandom update that derives the next blinding factor $x_{i+1}$, ensuring that the cryptographic elements $\A{i}$ remain unlinkable across layers.
\begin{equation}
(\s{1}, \s{2}, \s{3}) \quad \left\{ \quad
\begin{aligned}
    \A{i}    &= x_i \, G, \\
    \s{i}    &= \InverseMap{(x_i \, \PK{i})}, \\
    x_{i+1}  &= s_i \, x_i \quad (\text{mod}\ p),
\end{aligned}
\right.
\label{eq:shared_secret}
\end{equation}

ensuring that each address remains recoverable while being computationally indistinguishable from a random point.

\subsection{Semi-Trusted Third Party}

Each semi-trusted third party (STTP) receives from the client only a subset of the information required to construct the full DSphinx header. 
Specifically, it obtains a share of the destination address (EC point $\Delta$) and, for each node along the path, 
a share of its encoded address (EC point $\N{i}$), 
a share of its shared secret (scalar $\s{i}$), 
and the hash of its shared secret (scalar $\sHashed{i}$). 
Using these shares, each STTP independently constructs a \emph{partial} encrypted header. 
This computation proceeds in two stages: 
a preprocessing phase (Alg.~\ref{algo:preprocessing}, Fig.~\ref{fig:chunk-preprocessing}) that generates filler chunks, 
followed by a layer-by-layer encryption phase (Alg.~\ref{algo:sttp}, Fig.~\ref{fig:chunk-encryption}) applied in reverse order, from the last hop to the first.

% Preprocessing
\smallskip
\noindent\textbf{Preprocessing Phase.}
The preprocessing phase prepares a vector of filler chunks $\phi$ according to \eqref{eq:preprocessing}.
These filler chunks ensure that after each encryption layer the last two chunks evaluate to the identity element and can thus be safely truncated, ensuring a constant header size and reversibility at the network nodes. 
The detailed procedure is specified in Alg.~\ref{algo:preprocessing}, which takes as input the shares of the shared secrets $\{s_i\}$ and the chunk generators $\{G_j\}$, and outputs $n-1$ filler chunks, where $n = 2m+1$ is the header size for a path of length $m$. 
An example for $m=3$ is illustrated in Fig.~\ref{fig:chunk-preprocessing}.
\begin{equation}
    \phi_j = - \sum_{i=1}^{m} s_i\, G_{\,n+j-2i}, \qquad 1 \le j \le n-1 .
\label{eq:preprocessing}
\end{equation}

% Layers
\noindent{\textbf{Layered Encryption Phase.}}
After preprocessing, the STTP initializes the header $H$ by appending the filler chunks $\phi$ to the destination share $\D{}$, producing a $n$-chunks header.
It then applies layered encryption in reverse path order, from node $i = m$ down to $i = 1$, 
as illustrated in Fig.~\ref{fig:chunk-encryption} and detailed in Alg.~\ref{algo:sttp}.
\begin{enumerate}
    \item \textbf{Encrypt Chunks}: 
    Each chunk $j$ is encrypted according Eq.~\eqref{eq:layer_i}.
    The last two chunks can safely be truncated as they evaluate to the identity element.
    \begin{equation}
        H_{ij} = H_{(i+1,\,j)} + \sG{i}{j}
        \label{eq:layer_i}
    \end{equation}

    \item \textbf{Integrity Tag:} 
    The remaining chunks are used to compute the integrity as:
    \begin{equation}
        \C{i} = \sG{i}{} + \sum_{j=1}^{n-2} \big( \hashIt{\sHashed{i}}{j} \, \B{i}{j} \big)
        \label{eq:integrity}
    \end{equation}

    \item \textbf{Prepend Node Information}:
    The node address $\N{i}$ and the integrity tag $\C{i}$ are prepended to $H_i$, producing again a $n$-chunks header.
\end{enumerate}
% After processing the final layer (node 1), the STTP outputs the resulting encrypted header, which constitutes its partial contribution to the final DSphinx header.

% Integrity
\smallskip
\noindent\textbf{Integrity Mechanism.}
The integrity construction in \eqref{eq:integrity} combines a pseudorandom weighted sum, where the weights are derived from $\sHashed{i}$ via iterated hashing, 
with a blinding offset term $s_i G$ that prevents integrity tags from being linked by STTPs that know the weights.
The pseudorandom weights prevent adversaries from forging valid checksums, while the blinding offset preserves unlinkability.  
This design preserves homomorphism while ensuring unlinkability and integrity.

\subsection{Network Nodes}

Upon receiving a packet, node $i$ extracts the cryptographic element $\A{i}$, the integrity tag $\C{i}$, and the encrypted routing information $\B{i}{}$. 
As in the original Sphinx design, the node stores previously seen values of $\A{i}$ (until its private key is rotated) and discards the packet if a match is found, thereby preventing replay attacks. 
Otherwise, the packet is processed as illustrated in Fig.~\ref{fig:chunk-decryption}.

The node first derives the shared secret point by multiplying $\A{i}$ with its private key $\sk{i}$, and then recovers the corresponding scalar $\s{i}$ by applying the inverse Elligator mapping as in \eqref{eq:derive_secret}.
\begin{equation}
\begin{aligned}
    \s{i} &= \InverseMap{(\sk{i} \, \A{i})}
\end{aligned}
\label{eq:derive_secret}
\end{equation}

% Integrity verification
\noindent
The shared secret $\s{i}$ is then used to verify the integrity tag in \eqref{eq:integrity_check}. 
\begin{equation}
\C{i} \overset{\text{?}}{=} \sG{i}{} + \sum_{j=1}^{n-2} \big( \hashIt{\sHashed{i}}{j} \, \B{i}{j} \big)
\label{eq:integrity_check}
\end{equation}

% Decryption
If the verification fails, the packet is discarded. 
Otherwise, the node appends two identity chunks to the header and decrypts it as \eqref{eq:decrypt}.
\begin{equation}
\BB{i}{j} = \B{i}{j} - \sG{i}{j}
\label{eq:decrypt}
\end{equation}
The first decrypted chunk $\BB{i}{1}$ encodes the next node's IP address $\N{i+1}$, 
which is recovered via the inverse Elligator map and unpadding. 
The second chunk $\BB{i}{2}$ contains the integrity tag $\C{i+1}$ for the next hop, 
while the remaining chunks form the next encrypted routing information $\B{i+1}{}$.

% Update Alpha
Finally, it updates the cryptographic element according to \eqref{eq:shared_secret}
and forwards the packet with header $(\A{i+1},\, \B{i+1}{},\, \C{i+1})$ to the next node along the path.
\begin{equation}
\A{i+1} = s_i \, \A{i}
\label{eq:update_alpha}
\end{equation}

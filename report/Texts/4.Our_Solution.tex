\section{Protocol description}\label{sec:scheme}

% Overview
The proposed decentralized protocol distributes the Sphinx header construction across multiple semi-trusted third parties (STTPs). 
Figure~\ref{fig:overall_schema} illustrates the protocol in five steps.
(1) The client randomly selects a route and a secret nonce $x$, from which he derives a sequence of shared secrets.
Each shared secret is split into $m$ additive shares, alongside the IP addresses of the mixnodes and the final destination.
(2) Each set of shares is sent to $m$ different STTP, along with the necessary cryptographic elements.  
(3) Each STTP independently computes a \textit{partial} Sphinx header using its shares.  
(4) The client then aggregates these partial headers to reconstruct the final header. 
(5) Finally, the client encrypts the payload accordingly to the header and sends the message through the mixnet.

% Header structure - Chunks
In our decentralized Sphinx header construction, each piece of header information is represented as an elliptic curve (EC) point.
The header is thus divided into fixed-size chunks, as illustrated in Figure~\ref{fig:chunked_schema}, where each chunk corresponds to one EC point.
Each mixnode along the path adds two chunks: one encoding its IP address and another representing its integrity tag.
Without loss of generality, we consider paths of three mixnodes in this paper, resulting in a seven-chunks header (i.e. seven EC points), two per mixnode plus one additional chunk for the final destination's IP address.

% Elligator
Representing IP addresses as EC points requires a mapping between integers and elliptic curve points that is reversible.
We define a mapping $\Map{}$ from integers to curve points and its inverse $\InverseMap{}$, such that $\InverseMap{\Map{x}} = x$ for any integer $x$.
Traditional approaches map integers directly to the $x$-coordinate of a valid point, but such methods cover only about half of all possible integers.
We instead employ the Elligator mapping~\cite{bernstein2013elligator}, which allows any integer to be mapped onto the curve, while producing outputs that are uniformly distributed and computationally indistinguishable from random curve points.
\newline

% Transition with next subsections (the four main steps)
In summary, the protocol is organized into four main components, each described in the following subsections:
\begin{itemize}
    \item \textbf{Setup:} generation of independent random generators;
    \item \textbf{Client:} additive sharing of information to STTPs;
    \item \textbf{STTP:} encryption of shares into partial headers;
    \item \textbf{Mixnode:} decryption and forwarding of packets.
\end{itemize}


\subsection{Setup}

As discussed in Section~\ref{sec:security}, each chunk requires a distinct generator to preserve the scheme's security properties. 
We therefore define a set of seven generators $\{G_j\}$, one for each chunk $j$.

% Synchronization
In principle, the setup phase can be executed only once. 
However, to maintain security over time, the set of generators should be refreshed periodically. 
All entities (clients, mixnodes, and STTPs) must perform the setup phase to ensure synchronization of generators. 
To achieve synchronization, generators are derived from a common seed computed as the hash of the current timestamp, truncated to the chosen refresh interval, and incremented to differentiate generators.

% Independent
To preserve the scheme's security properties, the generators must be \emph{independent}, meaning that the scalar relationship between any two generators is unknown. 
Formally, no entity should know any $z_j \in \mathbb{Z}_N$ such that $G_j = z_j G$, where $G$ is the curve's base point. 
This property is guaranteed by using the Elligator mapping, which provides a uniform and pseudorandom mapping while ensuring that each $G_j$ is computationally \emph{independent} from $G$ and from the other generators.

% Clearing cofactor
A subtlety with Elligator is that it may map integers to points on the full curve group, not exclusively within the large prime-order subgroup (i.e. the subgroup generated by $G$). 
This could enable a \emph{small subgroup attack}, potentially leaking up to 3 bits of information. 
This can be prevented by \emph{clearing the cofactor}, i.e. each generator is multiplied by the curve's cofactor (8 for Curve25519) to ensure it lies in the prime-order subgroup.

% Formula
The resulting formula for the $j^{th}$ generator is therefore:
\begin{equation}
G_j = 8 \cdot \Map{\hash{\text{timestamp}} + j}.
\end{equation}


\subsection{Client}
 
To send a message to a specific destination, the client randomly selects a path through the mixnet and generates a nonce.
Using this nonce and the public keys of each mixnodes along the path, it derives a chain of shared secret integers (\s{1}, \s{2}, \s{3}) as follows:
\begin{equation}
(\s{1}, \s{2}, \s{3}) \quad \left\{ \quad
\begin{aligned}
    \A{i}    &= x_i \, G \\
    \S{i}    &= x_i \, \PK{i} \\
    \s{i}    &= \InverseMap{\S{i}} \\
    r_i      &= \hash{{\A{i}}_y \ \| \ {\S{i}}_y} \\ % still yes ? Verify with complexity section
    x_{i+1}  &= x_i \, r_i \quad (\text{mod}\ n)
\end{aligned}
\right.
\label{eq:shared_secret}
\end{equation}
where $x_1$ is the client's nonce, $\PK{i} = \sk{i}\,\G{}$ is the public key of the $i^{th}$ mixnode, $n$ is the subgroup order (i.e. $(n+1)\G{} = \G{}$), $\|$ denotes concatenation, and subscripts $_y$ refer to the $y$-coordinate of a point. 
Each scalar $r_i$ pseudo-randomizes $x_i$ for the next hop, ensuring that cryptographic elements $\A{i}$ remain unlinkable across mixnodes.

IP addresses are padded with random bits and mapped to elliptic curve points via Elligator, allowing later recovery of IP addresses.
These IP points and the shared secrets are then split into shares and distributed to $m$ different STTPs, along with a hash of each secret. % for integrity

Each STTP then independently computes a partial header from the received shares and returns it to the client. 
The client aggregates these partial headers by performing chunk-wise point additions to reconstruct the complete encrypted header.
Finally, the client sends the header along with \A{1} to the first mixnode from the path. 

\subsection{STTP}

To construct the partial encrypted header, each STTP receives the following information from the client:
\begin{itemize}
    \item a share of the destination address (EC point $ \Delta $);
    \item a share of each mixnode address in the path (EC points $ \N{i} $);
    \item a share of each shared secret (scalars $ \s{i} $);
    \item the hash of each shared secret (scalars $ \sHashed{i} $).
\end{itemize}

Using these data, the STTP builds a partial encrypted header by layering the routing information in reverse, starting from the last mixnode, as illustrated in Figure~\ref{fig:chunked_schema}.

At each layer, two new chunks are introduced: the mixnode's address (\N{i}) and the integrity tag (\C{i}).  
To preserve a fixed-length header while allowing mixnodes to reverse the operation (as in the original design), four additional \emph{filler chunks} are appended.  
These filler chunks are computed in such a way that at each layer, after applying the corresponding masking points (\sG{i}{j}\hspace{-1mm}), the last two chunks cancel out and become the identity point (i.e. point at infinity).  
This mechanism allows these two chunks to be safely truncated at each layer, ensuring a consistent header size while preserving reversibility for mixnodes.

To initialize the header, the STTP encrypts the destination point using the shared secret of the last mixnode and append the required filler chunks. 
Let $ \Delta $ be the partial destination point, \s{i} the partial shared secret corresponding to the $ i^\text{th} $ mixnode in the path, and $ G_j $ the $ j^\text{th} $ chunk's generator. 
The chunks for the last layer (assuming a 3-hop path) are computed as follows:
\begin{equation}
\B{3}{} \quad \left\{ \quad
\begin{aligned}
    \B{3}{1} &= \Delta       + \sG{3}{1} \\
    \B{3}{2} &= - (\sG{2}{4} + \sG{1}{6}) \\
    \B{3}{3} &= - (\sG{2}{5} + \sG{1}{7}) \\
    \B{3}{4} &= - \sG{2}{6} \\
    \B{3}{5} &= - \sG{2}{7} \\
\end{aligned}
\right.
\label{eq:last_layer}
\end{equation}

\noindent
Subsequent layers ($ i = 2 $ and $ i = 1 $) are computed with Eq. \ref{eq:layer_i} where \N{i+1} represents the 
elliptic curve point corresponding to the $ (i+1)^\text{th} $ mixnode in the path and \C{i+1} is the integrity tag from previous layer.
\begin{equation}
\B{i}{} \quad \left\{ \quad
\begin{aligned}
    \B{i}{1} &= \N{i+1} + \sG{i}{1}\\
    \B{i}{2} &= \C{i+1} + \sG{i}{2} \\
    \B{i}{3} &= \B{(i+1,}{1)} + \sG{i}{3} \\
    \B{i}{4} &= \B{(i+1,}{2)} + \sG{i}{4} \\
    \B{i}{5} &= \B{(i+1,}{3)} + \sG{i}{5} \\
\end{aligned}
\right.
\label{eq:layer_i}
\end{equation}

\noindent
For each layer, the integrity tag is computed with Eq. \ref{eq:integrity} where \hashIt{\sHashed{i}}{j} means hashing $j$ times \sHashed{i} which is the hash of the $i^{th}$ mixnode's complete shared secret.
The integrity tag consists in a pseudo-random weighted sum of the chunks, offset by a secret point derived from the shared secret integer.
The pseudo-random weights (i.e. \hashIt{\sHashed{i}}{j}) ensure binding, preventing adversaries from modifying individual chunks.
Without these weights, an attacker could add a random point P to one chunk and subtract P from another, thereby preserving the overall sum and bypassing the integrity check.
The secret offset (i.e. \sG{i}{}) prevents curious STTPs from correlating integrity tags.
Since STTPs are aware of these pseudo-random weights, omitting this offset would allow STTPs to potentially link some incoming and outgoing mixnode's packets by simply verifying integrity tags.
\begin{equation}
\C{i} = \sG{i}{} + \sum_{j=1}^{5} \big( \hashIt{\sHashed{i}}{j} \, \B{i}{j} \big)
\label{eq:integrity}
\end{equation}

When the first layer is finally computed, it is appended with the integrity tag \C{1} and the first mixnode's point $ N_1 $.
Finally, the STTP returns the resulting partial header to the client.

\paragraph{\textbf{Security Note.}}\label{note:security_why_indep_generators}
To preserve unlinkability, it is essential that the generators $ (\G{1}, \dots, \G{7}) $ are \textit{independent}, meaning their scalar relationships are unknown and computationally infeasible to derive.
If the same generator \G{} were used across chunks (or their scalar relationships known), an adversary could compute chunk-wise difference between consecutive layers: $ \B{i}{j} - \B{i+1}{j} = \sG{i}{} $.
Since the shared secret \s{i} remains consistent within a layer, the resulting differences would reveal a predictable pattern (uniform or preserved scalar relationships).
This consistency could allow an adversary to correlate incoming and outgoing packets at a mixnode, thereby breaking the unlinkability property.
Using independent generators for each chunk prevents such correlations and is therefore critical to the protocol's security.  


\subsection{Mixnode}
% 1) Extract information from the header
% 2) Recompute shared secret
% 3) Integrity check
% 4) Update encrypted information (β)
% 5) Update cryptographic element (α)

When a packet arrives at mixnode $i$, it begins by extracting the relevant header fields, namely the cryptographic element \A{i} and the integrity tag \C{i}.  
The mixnode then recomputes the shared secret point \S{i} using its private key \sk{i} and the cryptographic element \A{i}:  
\begin{equation}
\begin{aligned}
    \S{i} &= \sk{i} \, \A{i} \\
    \s{i} &= \InverseMap{\S{i}}\\
\end{aligned}
\label{eq:derive_secret}
\end{equation}
This shared secret point is subsequently mapped to the shared integer \s{i} using Elligator inverse mapping.
This shared integer is then used to verify the integrity tag (Eq. \ref{eq:integrity_check}).
\begin{equation}
\C{i} \overset{\text{?}}{=} \sG{i}{} + \sum_{j=1}^{5} \big( \hashIt{\s{i}}{j} \, \B{i}{j} \big)
\label{eq:integrity_check}
\end{equation}

\noindent If the integrity check passes, the mixnode pads the header by appending two \textit{identity} chunks (i.e. point at infinity) and then updates it as:
\begin{equation}
{\BB{i}{j}} = \B{i}{j} - \sG{i}{j} \qquad \forall j = 1, \dots, 7
\label{eq:decrypt}
\end{equation}

The first chunk $({\BB{i}{1}})$, encodes the next mixnode's IP address (\N{i+1}). 
This point is mapped back to an integer using Elligator and the random padding is removed by keeping the last 128 bits (i.e. size of an IP address).

\noindent The second chunk $({\BB{i}{2}})$ is the next integrity tag (\C{i+1}) for the remaining five chunks that form the new encrypted routing information $(\B{i+1}{})$.

To maintain unlinkability, the cryptographic element \A{i} must be updated for the next hop. 
As in the client's step, it is computed using the $y$-coordinates of both \A{i} and \S{i}:
\begin{equation}
\A{i+1} = \text{hash}({\A{i}}_y \ \| \ {\S{i}}_y) \ \A{i}
\label{eq:update_alpha}
\end{equation}
Finally, the mixnode forwards the updated header $(\A{i+1}, \C{i+1}, \B{i+1}{})$ to the next mixnode in the path.

\section{Protocol description}\label{sec:scheme}

% Overview
The proposed decentralized protocol distributes the Sphinx header construction across multiple semi-trusted third parties (STTPs). 
Figure~\ref{fig:overall_schema} illustrates the protocol in five steps.
(1) The client randomly selects a route and a secret nonce $x$, from which he derives a sequence of shared secrets.
Each shared secret is split into $t$ additive shares, alongside the IP addresses of the mixnodes and the final destination.
(2) Each set of shares is sent to $t$ different STTP, along with the necessary cryptographic elements.  
(3) Each STTP independently computes a \textit{partial} Sphinx header using its shares.  
(4) The client then aggregates these partial headers to reconstruct the final header. 
(5) Finally, the client encrypts the payload accordingly to the header and sends the message through the mixnet.

% Header structure - Chunks
In our decentralized Sphinx header construction, each piece of header information is represented as an elliptic curve (EC) point.
The header is thus divided into fixed-size chunks, as illustrated in Figure~\ref{fig:chunked_schema}, where each chunk corresponds to one EC point.
Each mixnode along the path adds two chunks: one encoding its IP address and another representing its integrity tag.
Without loss of generality, we consider paths of three mixnodes in this paper, resulting in a seven-chunks header (i.e. seven EC points), two per mixnode plus one additional chunk for the final destination's IP address.

% Elligator
Representing IP addresses as elliptic curve points requires a reversible mapping between integers and curve points.  
We define a mapping $\Map{}$ from integers to points and its inverse $\InverseMap{}$ such that $\InverseMap{\Map{x}} = x$ for any integer $x$.  
Classical encodings map an integer directly to the $x$-coordinate of a valid point, but it succeeds only for roughly half of integers and introduces structural bias. 
To avoid this issue, we rely on the Elligator mapping~\cite{bernstein2013elligator}, which deterministically maps any integer to a curve point while ensuring that the resulting points are uniformly distributed and computationally indistinguishable from randomly sampled points.  
This property allows IP addresses to blend seamlessly with other cryptographic elements of the Sphinx header.
\newline

% Transition with next subsections (the four main steps)
In summary, the protocol is organized into four main components, each described in the following subsections:
\begin{itemize}
    \item \textbf{Setup:} generation of independent random generators;
    \item \textbf{Client:} additive sharing of information to STTPs;
    \item \textbf{STTP:} encryption of shares into partial headers;
    \item \textbf{Mixnode:} decryption and forwarding of packets.
\end{itemize}


\subsection{Setup}

As discussed in Section~\ref{sec:indep_generators}, each chunk requires a distinct generator to preserve the scheme's security properties. 
We therefore define a set of seven generators $\{G_j\}$, one for each chunk $j$.

% Synchronization
In principle, the setup phase can be executed only once. 
However, to maintain security over time, the set of generators should be refreshed periodically. 
All entities (clients, mixnodes, and STTPs) must perform the setup phase to ensure synchronization of generators. 
To achieve synchronization, generators are derived from a common seed computed as the hash of the current timestamp, truncated to the chosen refresh interval, and incremented to differentiate generators.

% Independent
To preserve the scheme's security properties, the generators must be \emph{independent}, meaning that the scalar relationship between any two generators is unknown. 
Formally, no entity should know any $z_j \in \mathbb{Z}_N$ such that $G_j = z_j G$, where $G$ is the curve's base point. 
This property is guaranteed by using the Elligator mapping, which provides a uniform and pseudorandom mapping while ensuring that each $G_j$ is computationally \emph{independent} from $G$ and from the other generators.

% Clearing cofactor
A subtlety with Elligator is that it may map integers to points on the full curve group, not exclusively within the large prime-order subgroup (i.e. the subgroup generated by $G$). 
This could enable a \emph{small subgroup attack}, potentially leaking up to 3 bits of information. 
This can be prevented by \emph{clearing the cofactor}, i.e. each generator is multiplied by the curve's cofactor (8 for Curve25519) to ensure it lies in the prime-order subgroup.

% Formula
The resulting formula for the $j^{th}$ generator is therefore:
\begin{equation}
G_j = 8 \cdot \Map{\hash{\text{timestamp}} + j}.
\end{equation}


\subsection{Client}

To send a message to a chosen destination, the client first selects a random path through the mixnet and generates an initial nonce.  
Using this nonce and the public keys of the mixnodes along the route, the client derives a sequence of shared secrets \((\s{1}, \s{2}, \s{3})\)
according to Eq.~\ref{eq:shared_secret}, yielding a hop-by-hop key derivation.
\begin{equation}
(\s{1}, \s{2}, \s{3}) \quad \left\{ \quad
\begin{aligned}
    \A{i}    &= x_i \, G, \\
    \S{i}    &= x_i \, \PK{i}, \\
    \s{i}    &= \InverseMap{\S{i}}, \\
    x_{i+1}  &= s_i \, x_i \quad (\text{mod}\ n),
\end{aligned}
\right.
\label{eq:shared_secret}
\end{equation}
where $x_1$ is the client's nonce, $\PK{i} = \sk{i}\,\G{}$ is the public key of the $i^{th}$ mixnode, $n$ is the lagre prime subgroup order (i.e. $(n+1)\G{} = \G{}$), and $\InverseMap{}$ is the inverse Elligator, mapping EC point to integer.
The scalar $s_i$ provides as a per-hop pseudorandom update, ensuring that the cryptographic element $\A{i}$ remain unlinkable across layers.

Next, the client encodes the routing information for each hop
IP addresses are padded with random bits and mapped to elliptic curve points via Elligator, ensuring that each address can later be recovered while appearing indistinguishable from a random point.  
Both these IP points and the derived shared secrets are then additively split into $t$ shares.  
Each STTP receives one share of every value, together with the hash of derived shared secrets.

Each STTP independently processes its assigned shares and returns a \emph{partial} header to the client.  
The client aggregates these partial headers by performing chunk-wise elliptic-curve point additions, thereby reconstructing the complete encrypted Sphinx header.
Once aggregation is complete, the client attaches $\A{1}$ and sends the finalized header, together with the encrypted payload, to the first mixnode on the path.


\subsection{STTP}

Each STTP receives from the client a subset of the information required to construct the full Sphinx header.  
It obtains a share of the destination address (EC point $\Delta$), and for every mixnode along the path:
\begin{itemize}
    \item a share of its address (EC points $\N{i}$);
    \item a share of its shared secret (scalars $\s{i}$);
    \item the hash of its shared secret (scalars $\sHashed{i}$).
\end{itemize}

Using these shares, each STTP independently constructs a \emph{partial} encrypted header.  
As illustrated in Figure~\ref{fig:chunked_schema}, the construction proceeds layer by layer in reverse order, beginning with the last mixnode in the path and iterating backward toward the first.
\newline

% First layer
The construction of the last layer, corresponding to the final mixnode, follows a slightly different procedure. 
For a path of $m$ mixnodes, the destination chunk is first padded with $2(m-1)$ \emph{filler chunks}.  
These filler chunk values are computed so that, after the layer's masking points $\sG{i}{j}$ are applied, the last two chunks collapse to the identity point (depicted as a grey '0' block in Figure~\ref{fig:chunked_schema}).  
This ensures that at each subsequent layer these two chunks can be safely truncated, preserving a fixed header size while maintaining the reversibility required for mixnode processing.

Let $\Delta$ be the destination address share, $\s{i}$ the shared secret share for the $i^\text{th}$ mixnode in the path, and $G_j$ the $j^\text{th}$ generator.  
The chunks for the last layer (assuming a 3-hop path) are computed as:
\begin{equation}
\B{3}{} \quad \left\{ \quad
\begin{aligned}
    \B{3}{1} &= \Delta       + \sG{3}{1} \\
    \B{3}{2} &= - (\sG{2}{4} + \sG{1}{6}) \\
    \B{3}{3} &= - (\sG{2}{5} + \sG{1}{7}) \\
    \B{3}{4} &= - \sG{2}{6} \\
    \B{3}{5} &= - \sG{2}{7} \\
\end{aligned}
\right.
\label{eq:last_layer}
\end{equation}

% Non-first layers
Subsequent layers ($ i = 2 $ and $ i = 1 $) are computed with Eq. \ref{eq:layer_i} where \N{i+1} represents next hop address, 
and \C{i+1} is the integrity tag from previous layer.
Once the first layer is completed, the STTP outputs the resulting partial header to the client.
\begin{equation}
\B{i}{} \quad \left\{ \quad
\begin{aligned}
    \B{i}{1} &= \N{i+1} + \sG{i}{1}\\
    \B{i}{2} &= \C{i+1} + \sG{i}{2} \\
    \B{i}{3} &= \B{(i+1,}{1)} + \sG{i}{3} \\
    \B{i}{4} &= \B{(i+1,}{2)} + \sG{i}{4} \\
    \B{i}{5} &= \B{(i+1,}{3)} + \sG{i}{5} \\
\end{aligned}
\right.
\label{eq:layer_i}
\end{equation}

% Integrity
Because the integrity mechanism in our decentralized design must be homomorphic, the integrity tag is computed as a pseudorandom weighted checksum.
At each layer, the integrity tag which consists in a weighted sum of the chunks, offset by a secret point derived from the mixnode's shared secret, as shown in Eq.~\ref{eq:integrity}:
\begin{equation}
\C{i} = \sG{i}{} + \sum_{j=1}^{5} \big( \hashIt{\sHashed{i}}{j} \, \B{i}{j} \big)
\label{eq:integrity}
\end{equation}
where \hashIt{\sHashed{i}}{j} denotes hashing $j$ times \sHashed{i} which is the hash of the $i^{th}$ mixnode's full shared secret.

This construction combines two elements; a \emph{pseudo-random weighted sum}, and a \emph{blinding offset} term $s_i G$.  
The pseudo-random weights $\hashIt{\sHashed{i}}{j}$ prevent adversaries from modifying chunks while preserving the total sum.  
Without these weights, an attacker could add a random point $P$ to one chunk and subtract $P$ from another, keeping the overall sum unchanged and evading the integrity check.
The offset term $\sG{i}{}$ ensures privacy against corrupted STTPs.  
Since STTPs know the weights, omitting this offset would allow them to potentially link some incoming and outgoing mixnode's packets by simply verifying integrity tags.
The offset therefore blinds the checksum, preventing such correlation attacks while preserving homomorphism.

\subsection{Mixnode}
Upon receiving a packet, mixnode $i$ extracts the cryptographic element $\A{i}$, the integrity tag $\C{i}$, and the encrypted header chunks $\B{i}{}$.  
As in the original Sphinx design, the mixnode stores previously seen $\A{i}$ values (until its private key is rotated).
If the received $\A{i}$ matches a stored value, the packet is discarded to prevent replay attacks.  
If the value is fresh, the packet is processed as illustrated in Figure~\ref{fig:mixnode_decryption}.

The mixnode first reconstructs its shared secret point $\S{i}$ using its private key \sk{i}, and then maps this point to the corresponding shared integer $\s{i}$ using the Elligator inverse mapping:
\begin{equation}
\begin{aligned}
    \S{i} &= \sk{i} \, \A{i} \\
    \s{i} &= \InverseMap{\S{i}}\\
\end{aligned}
\label{eq:derive_secret}
\end{equation}

% Integrity verification
\noindent
This value $\s{i}$ is then used to verify the integrity tag:
\begin{equation}
\C{i} \overset{\text{?}}{=} \sG{i}{} + \sum_{j=1}^{5} \big( \hashIt{\s{i}}{j} \, \B{i}{j} \big)
\label{eq:integrity_check}
\end{equation}

% Decryption
If this check fails, the packet is discarded.
Otherwise, the mixnode pads the header by appending two \textit{identity} chunks (i.e. point at infinity) and then updates it as:
\begin{equation}
{\BB{i}{j}} = \B{i}{j} - \sG{i}{j} \qquad \forall j = 1, \dots, 7
\label{eq:decrypt}
\end{equation}

The first resulting chunk, $\BB{i}{1}$, encodes the next mixnode's IP address address (\N{i+1}).  
It is mapped back to an integer using the inverse Elligator map, after which the padding bits are removed.

The second chunk, $\BB{i}{2}$, becomes the integrity tag for the next hop ($\C{i+1}$).  
The remaining five chunks constitute the next encrypted routing information $(\B{i+1}{})$.

% Update Alpha
As specified in Eq.~\ref{eq:shared_secret}, the mixnode applies the same update rule as the client to compute the next cryptographic element $\A{i+1}$:
\begin{equation}
\A{i+1} = s_i \, \A{i}
\label{eq:update_alpha}
\end{equation}
Finally, the mixnode forwards the updated header $(\A{i+1}, \C{i+1}, \B{i+1}{})$ to the next mixnode in the path.

\section{Protocol Description}\label{sec:scheme}

% Overview
The proposed decentralized protocol distributes the Sphinx header construction across multiple semi-trusted third parties (STTPs). 
Fig.~\ref{fig:overall_schema} illustrates the protocol in five steps.
(1) The client randomly selects a route and a secret nonce $x$, from which he derives a sequence of shared secrets.
Each shared secret is split into $t$ additive shares, alongside the IP addresses of the nodes and the final destination.
(2) Each set of shares is sent to $t$ different STTP, along with the necessary cryptographic elements.  
(3) Each STTP independently computes a \textit{partial} Sphinx header using its shares.  
(4) The client then aggregates these partial headers to reconstruct the final header. 
(5) Finally, the client encrypts the payload accordingly to the header and sends the message through the decentralized network.

% Header structure - Chunks
In DSphinx, each header element is represented as an elliptic curve (EC) point. 
Accordingly, the header is divided into fixed-size chunks, as illustrated in Fig.~\ref{fig:chunked_schema}, with each chunk corresponding to a single EC point. 
Every network node along the path contributes for two chunks: one encoding its IP address and another representing its integrity tag. 
Thus, a path of length $m$ is represented by $n = 2m + 1$ chunks, accounting for two chunks per node and an additional chunk for the final destination.

% Elligator
Representing IP addresses as elliptic curve points requires a reversible mapping between integers and curve points.  
We define a mapping $\Map{}$ from integers to points and its inverse $\InverseMap{}$ such that $\InverseMap{(\Map{(x)})} = x$ for any integer $x$.  
Classical encodings map an integer directly to the $x$-coordinate of a valid point, but it succeeds only for roughly half of integers and introduces structural bias. 
To avoid this issue, we rely on the Elligator mapping~\cite{bernstein2013elligator}, which deterministically maps any integer to a curve point while ensuring that the resulting points are uniformly distributed and computationally indistinguishable from randomly sampled points.  
This property allows IP addresses to blend seamlessly with other cryptographic elements of the Sphinx header.

% Transition with next subsections (the four main steps)
% \smallskip
The DSphinx protocol is organized into four main components, each described in the following subsections:
%
\begin{itemize}
    \item \textbf{Setup:} generation of independent random generators;
    \item \textbf{Client:} additive sharing of information to STTPs;
    \item \textbf{STTP:} encryption of shares into partial headers;
    \item \textbf{Network nodes:} packets decryption and forwarding.
\end{itemize}

\subsection{Setup}

As discussed in Section~\ref{sec:indep_generators}, each chunk requires a distinct generator to preserve the scheme's security properties. 
We therefore define a set of $n$ generators $\{G_j\}_{j=1..n}$, one for each chunk $j$.

% Synchronization
In principle, the setup phase could be executed only once. 
However, to maintain security over time, the set of generators should be refreshed periodically. 
All entities (clients, nodes, and STTPs) must perform the setup phase to ensure synchronization of generators. 
To achieve synchronization, generators are derived from a common seed computed as the hash of the current timestamp, truncated to the chosen refresh interval, and incremented to differentiate generators.

% Independent
To preserve the scheme's security properties, the generators must be \emph{independent}, meaning that the scalar relationship between any two generators is unknown. 
Formally, no entity should know any $z_j \in \mathbb{Z}_p$ such that $G_j = z_j G$, where $G$ is the curve's base point. 
This property is guaranteed by using the Elligator mapping~\cite{bernstein2013elligator}, which provides a uniform and pseudorandom mapping while ensuring that each $G_j$ is computationally \emph{independent} from $G$ or other generators.

% Clearing cofactor
A subtlety with Elligator is that it may map integers to points on the full curve group, not exclusively within the large prime-order subgroup (i.e. the subgroup generated by $G$). 
This could enable a \emph{small subgroup attack}, potentially leaking up to 3 bits of information. 
This can be prevented by \emph{clearing the cofactor}, i.e. each generator is multiplied by the curve's cofactor (8 for Curve25519) to ensure it lies in the prime-order subgroup.
%
% Formula
The resulting formula for the $j^{th}$ generator is therefore:
\begin{equation}
G_j = 8 \cdot \Map{(\hash{\text{timestamp}} + j)}.
\end{equation}


\subsection{Client}
To send a message to a chosen destination, the client first selects a path accordingly to the routing protocol and generates an initial nonce.  
Using this nonce and the public keys of the nodes along the route, the client derives a sequence of shared secrets \((\s{1}, \s{2}, \s{3})\)
according to \eqref{eq:shared_secret}, yielding a hop-by-hop key derivation.
\begin{equation}
(\s{1}, \s{2}, \s{3}) \quad \left\{ \quad
\begin{aligned}
    \A{i}    &= x_i \, G, \\
    \s{i}    &= \InverseMap{(x_i \, \PK{i})}, \\
    x_{i+1}  &= s_i \, x_i \quad (\text{mod}\ p),
\end{aligned}
\right.
\label{eq:shared_secret}
\end{equation}
where $x_1$ is the client's nonce, $\PK{i} = \sk{i}\,\G{}$ is the public key of the $i^{th}$ node along the path, $p$ is the large prime subgroup order, and $\InverseMap{}$ is the inverse Elligator, mapping EC point to integer.
The scalar $s_i$ provides as a per-hop pseudorandom update, ensuring that the cryptographic element $\A{i}$ remain unlinkable across layers.

Next, the client encodes the routing information for each hop. 
IP addresses are padded with random bits and mapped to elliptic curve points via Elligator, ensuring that each address can later be recovered while appearing indistinguishable from a random point.  
Both these IP points and the derived shared secrets are then additively split into $t$ shares.  
Each STTP receives one share of every value, together with the hash of derived shared secrets.

Each STTP independently processes its assigned shares and returns a \emph{partial} header.  
The client aggregates these partial headers by performing chunk-wise EC additions, thereby reconstructing the complete encrypted DSphinx header.
Once aggregation is complete, the client attaches $\A{1}$ and sends the finalized header, together with the encrypted payload, to the first node on the path.


\subsection{Semi-Trusted Third Party}


Each semi-trusted third party (STTP) receives from the client only a subset of the information required to construct the full DSphinx header.
It obtains a share of the destination address (EC point $\Delta$), and for every node along the path:
\begin{itemize}
    \item a share of its address (EC points $\N{i}$);
    \item a share of its shared secret (scalars $\s{i}$);
    \item the hash of its shared secret (scalars $\sHashed{i}$).
\end{itemize}
Using these shares, each STTP independently constructs a \emph{partial} encrypted header.  
As illustrated in Fig.~\ref{fig:chunked_schema}, the computation proceeds in two stages: (i) a preprocessing phase that generates filler chunks, and (ii) a layer-by-layer encryption phase applied in reverse order, from the last hop to the first.


% Preprocessing
% \medskip
\noindent{\textbf{Preprocessing Phase.}}
The preprocessing step prepares a vector of filler chunks $\phi$ whose role is to cancel out during the encryption of successive layers, thereby ensuring a constant header size and enabling reversibility at the nodes. 
Algorithm~\ref{algo:preprocessing} takes as input the share of the shared secrets ${s_i}$ and the generators ${G_j}$ associated with each chunk $j$, and outputs $n-1$ filler chunks, where $n = 2m+1$ is the header size for a path of length $m$.
These filler chunks are computed according to \eqref{eq:preprocessing}, and ensure that after each encryption layer, the last two chunks evaluate to the identity element and can therefore be safely truncated.
The case $m=3$ is depicted in Fig.~\ref{fig:chunked_schema}.

\begin{equation}
    \phi_j = - \sum_{i=1}^{m} s_i\, G_{\,n+j-2i}, \qquad 1 \le j \le n-1 .
\label{eq:preprocessing}
\end{equation}

% Layers
\noindent{\textbf{Layered Encryption Phase.}}
After preprocessing, the STTP initializes the header $H$ by appending the destination share $\D{}$ with the filler chunks $\phi$, yielding a $n$-chunks header.
Then, proceeding from node $i = m$ down to $i = 1$, the STTP performs the following operations (Alg.~\ref{algo:sttp}):

% \begin{figure}
%     \centering
%     \resizebox{0.5\linewidth}{!}{\input{schema/chunkwise_encryption.tex}}
%     \caption{Chunk-wise header encryption for a path of length $m=3$. Circled numbers \eq[\color{red}x] refers to Equation x in the paper.}
%     \label{fig:chunked_schema}
% \end{figure}

\begin{enumerate}
    \item \textbf{Encrypt Chunks}: 
    Every chunk $j$ is encrypted as:
    \begin{equation}
    H_{ij} = H_{(i+1,\,j)} + \sG{i}{j}
    \label{eq:layer_i}
    \end{equation}
    The last two chunks, which evaluate to the identity element, are safely truncated.
    \item \textbf{Compute Integrity:} 
    The remaining $n-2$ chunks are used to compute the integrity tag as:
    \begin{equation}
        \C{i} = \sG{i}{} + \sum_{j=1}^{n-2} \big( \hashIt{\sHashed{i}}{j} \, \B{i}{j} \big)
        \label{eq:integrity}
    \end{equation}
    \item \textbf{Prepend Node Information}:
    The node address $\N{i}$ and the integrity tag $\C{i}$ are prepended to $H_i$, producing a $n$-chunks header.
\end{enumerate}
After processing the first node, the STTP outputs the resulting encrypted header, which constitutes its partial contribution to the final DSphinx header.

% Integrity
% \medskip
\noindent{\textbf{Integrity Mechanism.}}
The integrity construction in \eqref{eq:integrity} combines two essential components:
\begin{itemize}
\item a \emph{pseudorandom weighted sum} where weights are derived from $\sigma_i$ through iterated hashing;
\item a \emph{blinding offset} term $s_i G$, ensuring that integrity tags remain unlinkable to STTPs that know the weights.
\end{itemize}
The pseudorandom weights prevent adversaries from introducing compensating modifications across chunks that preserve the checksum.
The blinding offset prevents STTPs from using their knowledge of the weights to correlate integrity tags across packets.
This design preserves homomorphism while ensuring unlinkability and integrity.


\subsection{Network Nodes}
Upon receiving a packet, node $i$ extracts the cryptographic element $\A{i}$, the integrity tag $\C{i}$, and the encrypted routing information $\B{i}{}$.  
As in Sphinx design, the node stores previously seen $\A{i}$ values (until its private key is rotated).
If the received $\A{i}$ matches a stored value, the packet is discarded to prevent replay attacks.  
If the value is fresh, the packet is processed as illustrated in Fig.~\ref{fig:mixnode_decryption}.

The node first reconstructs its shared secret point using its private key \sk{i}, and maps it to the corresponding shared integer $\s{i}$ using the Elligator inverse mapping \eqref{eq:derive_secret}.
\begin{equation}
\begin{aligned}
    \s{i} &= \InverseMap{(\sk{i} \, \A{i})}
\end{aligned}
\label{eq:derive_secret}
\end{equation}

% Integrity verification
\noindent
This value $\s{i}$ is then used to verify the integrity tag \eqref{eq:integrity_check}.
\begin{equation}
\C{i} \overset{\text{?}}{=} \sG{i}{} + \sum_{j=1}^{n-2} \big( \hashIt{\sHashed{i}}{j} \, \B{i}{j} \big)
\label{eq:integrity_check}
\end{equation}

% Decryption
If this check fails, the packet is discarded.
Otherwise, the node appends the header with two \textit{identity} chunks (i.e. point at infinity).
The header is then decrypted as \eqref{eq:decrypt}.
\begin{equation}
\BB{i}{j} = \B{i}{j} - \sG{i}{j}
\label{eq:decrypt}
\end{equation}
The first resulting chunk $\BB{i}{1}$ encodes the next node's IP address (\N{i+1}).  
It is mapped back to an integer using the inverse Elligator map, after which the padding bits are removed.
The second chunk $\BB{i}{2}$ encodes the integrity tag for the next node ($\C{i+1}$).  
The remaining chunks constitute the next encrypted routing information $(\B{i+1}{})$.

% Update Alpha
As specified in \eqref{eq:shared_secret}, the node applies the same update rule as the client to compute the next cryptographic element $\A{i+1}$:
\begin{equation}
\A{i+1} = s_i \, \A{i}
\label{eq:update_alpha}
\end{equation}
Finally, the node forwards the updated packet with header $(\A{i+1},\, \B{i+1}{},\, \C{i+1})$ to the next node in the path.

\section{Security Analysis}

This section outlines the security guarantees of our scheme.  
We first analyze each desired property in an ideal setting (i.e. without collusion), and then discuss the effect of potential collusion, whether involving TTPs, mixnodes, or both.

We group the security properties into two categories: \emph{privacy} and \emph{robustness}.  
Privacy properties ensure that an adversary cannot infer metadata or communication patterns from packet observations.  
The main objective is to achieve \emph{unlinkability}, i.e. preventing any inference about who is communicating with whom.  
Robustness properties ensure that the system remains secure under active attacks such as packet replay, rerouting, or forgery.



\subsection{Privacy Properties}

We consider three main privacy properties:
\begin{itemize}
  \item \textbf{Fixed-size:}  
  All packets must have the same size, independent of header or payload length.  
  This prevents adversaries from correlating packets based on observable size patterns.
  \item \textbf{Unlinkability:}  
  An adversary cannot determine which outgoing packet corresponds to which incoming packet at a mixnode.
  \item \textbf{Relationship anonymity:}  
  It must be infeasible for an adversary to simultaneously identify both the sender and receiver of a communication, thus protecting sender-receiver relationship from being exposed.
\end{itemize}

These privacy properties are hierarchically dependent.  
Without \textit{fixed-size} packets, an adversary could correlate mixnode's incoming and outgoing packets by observing size patterns.
If an adversary is able to link an incoming packet to its corresponding outgoing packet at any mixnode, the entire communication path can be reconstructed, thereby breaking \textit{relationship anonimity}. 

Ensuring fixed-size packets is therefore a necessary condition which is already implicitly verified by our Python implementation, where packet size is determined by the system parameters.
Packets with unexpected size are discarded.


\subsubsection{Unlinkability}

The \emph{unlinkability} property requires that an adversary cannot determine, with more than negligible advantage, which outgoing packet corresponds to which incoming packet at a mixnode. 
Formally, if $n$ packets enter a mixnodes and $n$ packets leave it, the adversary's probability of correctly linking an incoming packet to its corresponding outgoing packet must satisfy
$$
\Pr[\text{linking}] \;\leq\; \frac{1}{n} + \epsilon,
$$
where $\epsilon$ is a negligible term. 
Intuitively, this means that even if the adversary colludes with the preceding and following mixnodes, its best strategy should be no better than random guessing.

There are two possible approaches to link a mixnode's incoming and outgoing packets:
\begin{itemize}
  \item Correlation through cryptanalysis;
  \item Correlation of header elements ($\alpha$, $\beta$, $\gamma$).
\end{itemize}

To prevent statistical correlation through cryptanalysis, packet headers must be computationally indistinguishable from random bitstrings.  
Empirical validation using the NIST statistical test suite confirms that generated headers exhibit strong randomness properties, making such correlation attacks highly improbable.

\paragraph{Linking via $\alpha$ values.}  
The relation $\alpha_{i+1} = s_i \alpha_i$ reveals no link unless the shared secret $s_i$ is recovered, which is computationally equivalent to solving the Elliptic Curve Discrete Logarithm Problem (ECDLP).  
If an adversary could compute $s_i$, verifying whether two packets are linked would become trivial.  
Moreover, mixnodes reject any packet with a repeated $\alpha$ value, preventing trivial replay-based linkage.

\paragraph{Linking via $\beta$ values.}  
For each chunk $j$, the difference between $\beta$ components of an incoming and its corresponding outgoing packet satisfies
$$
\beta_{(i,j)} - \beta_{(i+1,j-2)} = s_i G_j, \quad\quad \forall j \in \{1, \dots, 7\},
$$
where $\beta_{(i,-1)} = N_i$, $\beta_{(i,0)} = \gamma_i$, $\beta_{(i,6)} = 0G$, and $\beta_{(i,7)} = 0G$.  
To establish a link, the adversary must recover $s_i$ to verify cross-chunk consistency  (i.e. same $s_i$ value used), again reducing the problem to solving the ECDLP.  
This argument holds only under the assumption that the generators $G_j$ are independent (i.e. no scalar relationship between two generators is known to any participant).  
If an adversary finds a scalar $x$ such that $G_j = x G_{j'}$ for some $j \neq j'$, they could trivially test whether this relationship is preserved between packets, bypassing the ECDLP.  
Our setup phase prevents this by deriving independent generators using hashes and Elligator to map to a random EC point. 

\paragraph{Linking via $\gamma$ values.}  
The integrity tag $\gamma_i$ is computed as a weighted sum of header chunks:
$$
\C{i} = s_i G + \sum_{j=1}^{5} \big( h^{(j)}(s_i) \, \B{i}{j} \big).
$$
Linking $\gamma$ values therefore requires knowledge of the shared secret $s_i$ or its derived weights $h^{(j)}(s_i)$, which is infeasible in the absence of collusion.

\paragraph{Conclusion and assumptions.}  
Breaking unlinkability necessarily reduces to solving the ECDLP, under the following assumptions:
\begin{itemize}
  \item $\alpha$ values are used as nonces, and mixnodes discard packets with repeated $\alpha$ values;
  \item The generators $G_j$ are independent, as ensured by the setup procedure.
\end{itemize}

\paragraph{Security remark.}  
The independence of generators is a critical assumption.  
If an adversary discovers any scalar relation between two generators (i.e. solves a single instance of the ECDLP), the unlinkability of all packets in the system is compromised.  
To mitigate this, it is essential that the setup phase produces independent generators and that these generators are periodically refreshed.


\subsubsection{Relationship Anonymity}  

\emph{Relationship anonymity}, also known as \emph{sender-receiver unlinkability}, ensures that an adversary cannot associate a sender with its corresponding receiver.  
Assuming \emph{unlinkability} holds, the only remaining strategy for an adversary is to directly identify the final node.

In our scheme, the only information that could reveal a node's identity is its encoded IP address, represented as an elliptic curve point ($N_i$ for intermediate nodes or $\Delta$ for the final destination) via a reversible mapping such as Elligator.  
An adversary who obtains $N_i$ could trivially identify the corresponding node.  
However, in our construction, each $N_i$ is masked by at least one elliptic curve point of the form $s_{i-1} G_1$.  
Thus, deanonymizing $N_i$ reduces to guessing a candidate among all mixnodes in the system, solving an instance of the ECDLP for each guess, and checking consistency with the rest of the header, an infeasible task under standard cryptographic assumptions.  
The destination $\Delta$ is treated as the last node $N_{\text{last}}$ in the path.



\subsection{Robustness}  

We consider four main robustness properties:
\begin{itemize}
    \item \textbf{Integrity-forgery resistance:} 
    An adversary must not be able to modify a valid packet and simultaneously update its integrity tag such that the modified packet is still accepted by following mixnodes.   

    \item \textbf{Bounded path length:}
    The path length of a packet must be bounded to prevent excessively long or cyclic routes.   
    This bound ensures termination and limits the computational resources consumed per packet.

    \item \textbf{Wrap resistance:}\label{wrap_resistance}
    An adversary must not be able to transform a header $(\alpha, \beta, \gamma)$ into a new valid header $(\alpha', \beta', \gamma')$ such that, after being processed by some mixnode $i'$, the packet becomes $(\alpha, \beta, \gamma)$ again.  
    Without this property, an adversary could \textit{wrap} traffic around intermediate nodes arbitrarily many times, violating the bounded-path guarantee.  

    \item \textbf{Replay resistance:}
    A packet that has already been processed must be discarded if replayed, rather than being accepted again.  
    This prevents denial-of-service attacks in which an adversary floods the system by resending previously valid packets. 
\end{itemize}  

\emph{Replay resistance} and \emph{wrap resistance} can be reduce to \emph{integrity-forgery resistance}. 
\emph{Replay resistance} is inherited from the original Sphinx construction since mixnodes maintain a table of previously seen $\alpha$ values and discard replayed values (with tables reset only when keys are updated).\todo{Need to mention it in the schema}
Thus, if an adversary want to replay a packet, he would need to alter $\alpha$ (and consequently $\beta$) while still producing a consistent integrity tag $\gamma$, which directly reduces to the problem of forging integrity.  
Similarly, \emph{wrap resistance} also requires producing a modified header that passes integrity verification, meaning that it is reductible to integrity forgery.  


\subsubsection{Integrity-Forgery Resistance}\label{security:integrity_resistance}

Integrity (or forgery resistance) guarantees that any unauthorized modification of a packet will be detected by the next mixnode.  

Due to the decentralized nature of our scheme, we require a homomorphic integrity mechanism (i.e. integrity tags of TTP's partial headers are aggregated into the final header's integrity tag).
To achieve this, we employ a pseudorandom weighted checksum of the form:
$$
\C{i} = s_i G + \sum_j h^{(j)}(s_i)\, B_{(i,j)},
$$
where $B_{(i,j)}$ denotes the $j$-th header chunk, $s_i$ is the shared secret, and $h^{(j)}(s_i)$ is the $j$-th iterated hash of $s_i$.  
This construction combines two elements: (i) a \emph{weighted sum}, and (ii) a blinding \emph{offset} term $s_i G$.  
\newline


Each header chunk $\beta_{i,j}$ can be modified by an adversary in two possible ways: 
either (i) the chunk is replaced by a new point $\beta'_{i,j}$, or (ii) it is incremented by an elliptic curve point $P_j$.

\paragraph{Case 1: Chunk replacement.}
Replacing $\beta_{i,j}$ with $\beta'_{i,j}$ requires updating the corresponding integrity tag $\gamma_i$ to $\gamma'_i$ such that:
$$
\gamma'_i = \gamma_i + h^{(j)}(s_i)\, (\beta'_{i,j} - \beta_{i,j}).
$$
This operation necessitates knowledge of the weight $h^{(j)}(s_i)$, which is derived from the shared secret $s_i$. 
Without this information, an adversary cannot produce a valid updated integrity tag.

\paragraph{Case 2: Incremental modification.}
If the adversary only adds a point $P_j$ to a single chunk, the integrity tag must be updated as:
$$
\gamma'_i = \gamma_i + h^{(j)}(s_i)\, P_j,
$$
which again requires knowledge of the corresponding weight $h^{(j)}(s_i)$.

\paragraph{Case 2.b: Balanced increment.}
A more sophisticated attempt consists in modifying two chunks, say $j$ and $j'$, to preserve the checksum balance:
$$
\gamma'_i = \gamma_i + h^{(j)}(s_i)\, P_j + h^{(j')}(s_i)\, P_{j'}
$$
If the adversary knows a scalar $n$ such that $h^{(j)}(s_i) = n\,h^{(j')}(s_i)$,  it becomes:
$$
\gamma'_i = \gamma_i + h^{(j')}(s_i)\, (n P_j + P_{j'})
$$
Thus, the adversary can choose any $P_j$ and set $P_{j'} = -n P_j$, keeping $\gamma'_i = \gamma_i$ unchanged and thereby forging integrity.  

\paragraph{Conclusion.}
In summary, successful integrity forgery requires at least knowledge of scalar relations between the weights $h^{(j)}(s_i)$.  
Since these weights are derived from one-time shared secrets through iterated hashing, such relations are computationally infeasible to obtain in the absence of collusion.

\subsection{Collusion Analysis}\label{sec:collusion}

To complement decentralization with trusted third parties (TTPs), we must analyze the system's resilience to collusion. 
An adversary should not gain a decisive advantage by colluding with other entities. 
In our scheme, collusion can occur with: TTPs, mixnodes, or both.

\paragraph{Collusion with TTPs.}\label{sec:collusion-ttps} 
Collusion with a trusted third party (TTP) reveals three types of information:  
\begin{itemize}
  \item additive shares of destinations $N_{(i,t)}$, such that $N_i = \sum_{t=1}^T N_{(i,t)}$;  
  \item additive shares of shared secrets $s_{(i,t)}$, such that $s_i = \sum_{t=1}^T s_{(i,t)}$;
  \item hash values of the shared secrets $\{h(s_1), h(s_2), h(s_3)\}$.  
\end{itemize}

Since the first two items are additive shares, they provide no information unless all $T$ shares are collected.  
Hence, as long as at least one TTP remains honest, neither destinations nor shared secrets can be reconstructed.  
The only additional information available to an adversary colluding with a single TTP is the set of hash values $h(s_i)$, which determine the weights used in the checksum integrity tags.  
However, the integrity's blinding offset $s_i G$ prevents linking weights to specific packets.
Without this association, the adversary can only attempt modifications on a random packet, succeeding with probability $1/n$ among $n$ packets in the mixnet.

\paragraph{Collusion with mixnodes.}\label{sec:collusion-mixnodes}   
Collusion with a mixnode $i$ reveals its private key. 
This enables the adversary to compute the shared secret $s_i$, breaking unlinkability \emph{at that node}.  
However, since the node is already corrupted, this provides no additional power: the adversary cannot extend this knowledge beyond the compromised node.  
Therefore, the scheme remains secure as long as at least one mixnode on the path is honest, though the anonymity set is slightly reduced.  


\paragraph{Collusion with both TTPs and mixnodes.}\label{sec:collusion-all}
Collusion with both a TTP and a mixnode is more damaging.  
While TTPs alone reveal only unlinked weights, and mixnodes alone reveal only its shared secrets, their combination allows an adversary to \emph{link integrity weights to specific packets}.  
Indeed, the adversary can hash the mixnode's shared secret and match it against the TTP-provided weights, thereby recovering the corresponding weights for that packet across all mixnodes.  

This capability enables two attacks:\todo{Extend it with a bit of math}  % TODO
(i) \emph{Integrity forgery}: the adversary can modify chunks, including the final destination $\Delta$, while recomputing valid integrity tags as demonstrated in section \ref{security:integrity_resistance}.  
(ii) \emph{Weaker unlinkability}: the adversary may attempt to trace a packet by modifying it, updating the integrity tag, and checking if it succeeds integrity verifications.
This succeeds with probability $1/n$ and fails with probability $(n-1)/n$, where $n$ is the mixnode's batch size.
(iii) \emph{Mixnode position identification}: a mixnode colluding with a TTP can infer its exact position within the packet's path thanks to the weights. 
(iv) \emph{Breaking relationship anonymity}: if an adversary compromises both the entry and exit mixnodes of a packet, as well as one of the TTPs involved in constructing its header, 
then by correlating the integrity weights, the adversary can link the entry and exit nodes belonging to the same packet.  
This breaks relationship anonymity since the entry node reveals the sender and the exit node reveals the receiver.

\paragraph{Summary.}  
Collusion with either TTPs or mixnodes alone does not compromise security.
TTPs reveal only additive shares and unlinked weights, while mixnodes reveal only its shared secrets.  
However, collusion between a TTP and a mixnode is more powerful, as it enables linking weights to packets which allows integrity forging.  
Unlinkability remains computationally hard to break, but the adversary may probabilistically test packets with success probability $1/n$, where $n$ is the mixnode's batch size. 
In the worst case scenario (i.e. collusion between the TTP, and both entry and exit mixnodes), the relationship anonymity is compromised.
In summary, the security of the scheme rests on the following minimal assumptions:
(i) at least one TTP remains honest;
(ii) at least one mixnode on the path is not compromised; and
(iii) adversaries cannot simultaneously collude with both a TTP and a mixnode (in particular, when entry and exit nodes are corrupted).
Under these conditions, collusion yields at most negligible advantage beyond trivial guessing.

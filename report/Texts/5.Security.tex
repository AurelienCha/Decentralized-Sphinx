\section{Security Analysis}\label{sec:security}

This section analyzes the security guarantees of DSphinx and the assumptions under which they hold. 
We first study packet unlinkability, which constitutes the primary anonymity objective inherited from Sphinx, followed by integrity guarantees, the security of the decentralized route sampling mechanism, and relevant collusion scenarios. 
We assume that the Elliptic Curve Discrete Logarithm Problem (ECDLP) is hard in the underlying group, that hash functions are modeled as random oracles, that HMAC is existentially unforgeable under chosen-message attacks, 
that the hash-to-curve used to compute $\A{}$ does not reveal any exploitable discrete-log structure (i.e. not-reversible), and that no efficient adversary can recover scalar relations induced by the Elligator-based derivation procedure.

\subsection{Unlinkability}\label{sec:unlinkability}

To argue about sender-receiver unlinkability, we assume that an adversary cannot link a sender to its recipient without retracing the entire communication path.  
Thus, the problem reduces to proving unlinkability at the node level, meaning that an adversary cannot determine which outgoing packet corresponds to a given incoming packet.

We formalize unlinkability via a standard indistinguishability game between a challenger $\mathcal{C}$ and an adversary $\mathcal{A}$.
Intuitively, the adversary $\mathcal{A}$ observes packets entering and leaving a node and attempts to determine which outgoing packet corresponds to a given incoming packet.
The scheme provides unlinkability if any probabilistic polynomial-time adversary achieves only a negligible advantage over random guessing, i.e. $\Pr[a = c] - \frac{1}{2}$ is negligible.
% under the hardness of the underlying elliptic curve assumptions.

\medskip
\noindent\textbf{Game Definition:}
\begin{enumerate}[topsep=1pt, itemsep=1pt]
  \item \textbf{Setup.}
  The challenger generates the node's secret keys and public system parameters $(G_1, \dots, G_n)$ as in the setup phase, ensuring all generators $G_j$ are independent and uniformly distributed EC points.
  Generators are said to be independent if no participant knows any scalar relations among them.

  \item \textbf{Oracle.}  
  The adversary is granted access to an oracle, which on input of a nonce $x$ and routing path $\pi = (N_1, \ldots, N_m, \Delta)$ outputs a valid header $(\alpha, \beta, \gamma)$ and its updated form $(\alpha', \beta', \gamma')$ after being processed by the node.

  \item \textbf{Challenge.}
  The adversary submits two distinct headers $(\alpha_0, \beta_0, \gamma_0)$ and $(\alpha_1, \beta_1, \gamma_1)$ that were not obtained during oracle queries.  
  The challenger selects a random bit $c \in \{0,1\}$ and processes $(\alpha_{c}, \beta_{c}, \gamma_{c})$ through the node, obtaining $(\alpha'_{c}, \beta'_{c}, \gamma'_{c})$, which is then given to the adversary.

  \item \textbf{Guess.}
  The adversary outputs a bit ${a} \in \{0,1\}$, attempting to guess which input headers corresponds to the given output header.  
  He wins if ${a} = {c}$.
\end{enumerate}

\medskip
\noindent\textbf{Proof Sketch:}
As in the original Sphinx construction, all packets have a fixed size, preventing any adversary from correlating packets based on observable size patterns.
%In addition, headers are computationally indistinguishable from random bitstrings, as empirically confirmed by the NIST randomness test suite (Section~\ref{sec:NIST}).
Consequently, any successful distinguishing strategy must exploit correlations between header components $(\alpha, \beta, \gamma)$ across layers.
Since the integrity tag $\gamma$ is computed independently at each layer, it cannot be used for cross-layer linkage.

\smallskip
\noindent{\textbf{Case 1: Linking via $\boldsymbol\alpha$.}}  
Network nodes reject packets with duplicate $\alpha$ values, preventing trivial replay-based linkage.
The only relation between $\alpha$ and its processed form $\alpha'$ is the node's shared secret $s$.
Recovering $s$ from $\alpha' = s\alpha$ requires solving an instance of the Elliptic Curve Discrete Logarithm Problem.

\smallskip
\noindent{\textbf{Case 2: Linking via $\boldsymbol\beta$.}}\label{sec:indep_generators}  
Each header chunk $\beta_j$ and its corresponding processed value $\beta'_j$ satisfy $\beta_j - \beta'_j = s G_j$ for all $j \in \{1,\dots,n\}$.
To establish a link, $\mathcal{A}$ must determine whether the scalar relationship between two chunks is preserved.
When generators are independent, it reduces to solving an instance of the ECDLP, either to recover $s$ or to determine $z$ such taht $G_j = z G_{j'}$ between two chunk generators.

\smallskip
\noindent\textbf{Summary.}  
Under the ECDLP hardness assumption and assuming independent generators, no probabilistic polynomial-time adversary can achieve a non-negligible advantage in the unlinkability game.
Therefore, we can conclude that the proposed scheme provides unlinkability.

\subsection{Integrity, Replay and Wrap Resistance}\label{sec:integrity_forgery}

Packet integrity relies on a keyed HMAC computed using the network node shared secret.
An adversary modifying any component of a packet header must therefore generate a valid replacement tag in order for the modified packet to be accepted by an honest node.
Without knowledge of the corresponding secret key, forging such a tag is computationally infeasible under the standard security assumptions of HMAC.
Consequently, any modification of a packet header is detected with overwhelming probability.

\smallskip
\noindent\textbf{Replay Resistance.}\label{replay_resistance}
As in Sphinx, nodes maintain a replay cache containing previously observed values of $\alpha$.
Any packet containing a duplicate value is immediately discarded.
This prevents replay attacks intended to correlate traffic flows or influence packet processing.

\smallskip
\noindent\textbf{Wrap Resistance.}\label{wrap_resistance}
The original Sphinx construction provides wrap resistance, meaning that an adversary cannot transform a packet
$(\A{},\B{}{},\C{})$ into a packet $(\A{}',\B{}{}',\C{}')$ that decrypts back into the original packet after processing.
In DSphinx, such an attack would require modifying a packet while still producing a valid integrity tag.
Therefore, wrap resistance reduces directly to integrity-forgery resistance.

\subsection{Route Sampling Security}

A primary objective of DSphinx is to prevent clients from arbitrarily selecting routing paths while ensuring that STTPs cannot influence route selection. 
A route sampling mechanism is said to be fair if no probabilistic polynomial-time adversary can significantly increase the probability that a specific node appears in a sampled route beyond its probability under uniform random sampling. 
Under the preimage resistance of the route selection hash function and the confidentiality of node pseudonyms, DSphinx satisfies route sampling fairness, 
since clients only control the nonce used to derive $\A{}$, while STTPs do not influence the inputs of the route selection function.
consequently, neither party can meaningfully bias the probability of selecting any specific node beyond the uniform sampling baseline.

\smallskip
\noindent\textbf{Client Route Biasing.}
As described in Section~\ref{sec:path_sampling}, routing decisions are derived by hashing the tuple composed of the elliptic-curve point $\A{}$, a timestamp, and the hop index.
The timestamp and hop index are fixed by the protocol, leaving the nonce $w$, from which $\A{}$ is derived, as the only parameter under the client's control that can influence route selection.
Consequently, a malicious client seeking to bias route selection towards a particular node must search for a nonce that produces a desired routing outcome.
This reduces to a preimage-search problem on the route selection hash function.
Moreover, the client does not know the pseudonyms used during route selection unless it colludes with an STTP, nor can it associate pseudonyms with physical network nodes without collusion from those nodes.
Therefore, even if the client could influence the sampling process, it would generally be unable to predict which network node would be selected.

Beyond brute-force nonce search, the protocol must also prevent clients from introducing exploitable discrete-log structure into the route sampling process.
To this end, clients provide a nonce $w$, which is mapped to the elliptic-curve point $\A{}$ using a proper hash-to-curve function rather than an invertible encoding.
If a client could force $\A{}=xG$ for a known scalar $x$, then for any network node with secret key $k_i$ the corresponding shared secret would satisfy $S_i=k_ixG$.
The client could therefore compute $x^{-1}S_i=k_iG$, obtaining a reusable node-specific public point.
Although this does not reveal $k_i$, it enables the client to derive valid shared secrets involving that node in future protocol executions without further interaction with the STTPs, thereby circumventing the decentralized route sampling mechanism.
Using a non-invertible hash-to-curve mapping prevents this attack.


\smallskip
\noindent\textbf{STTP Route Biasing.}
The route is derived solely from the client-provided cryptographic material, the timestamp, and the hop index.
As a result, honest execution leaves no opportunity for an STTP to influence route selection.
If an STTP deviates from the protocol and returns inconsistent information, the resulting packet becomes invalid and is rejected by the network.
To tolerate malicious STTPs, clients may query more than the reconstruction threshold $d$ and reconstruct the required information from any honest subset.

\smallskip
\noindent\textbf{STTP Knowledge of Routes.}
Although STTPs participate in route generation, they do not know the mapping between node pseudonyms and actual network identities.
Consequently, observing that a route contains a pseudonym $r_i$ does not reveal which physical node is involved.
Nevertheless, STTPs may still learn limited information from traffic patterns. 
In particular, if multiple routes contain the same set of pseudonyms, an STTP can infer that the same route has been selected on multiple occasions, even though the identities of the corresponding nodes remain unknown.
However, in the absence of route biasing, such observations provide limited information because routes are generated pseudorandomly.
This highlights the importance of route sampling fairness: if route selection could be manipulated, repeated pseudonym patterns would become significantly more informative.

\subsection{Collusion Analysis}\label{sec:collusion}

We now analyze the impact of relevant collusion scenarios between entities involved in the protocol.

\smallskip
\noindent\textbf{Threshold STTP Compromise.}
The most severe scenario occurs when at least $d$ STTPs collude, where $d$ denotes the reconstruction threshold.
In this case, the adversary can reconstruct all network node secrets.
This compromises the security of the entire system.
Accordingly, the threshold parameter $d$ must be chosen such that collusion of this magnitude remains unrealistic.

\smallskip
\noindent\textbf{STTP - Network Node Collusion.}
A collusion between an STTP and a network node reveals the mapping between that node's pseudonym and its real identity, resulting in partial deanonymization of the routing space. 
While a single collusion does not yield a meaningful advantage, multiple colluding nodes may enable partial identification of sampled routes. 
From the network node's perspective, learning pseudonyms associated with other nodes may enable attempts to optimize its own pseudonym value.
Assuming honest nodes choose pseudonyms uniformly at random, any such advantage remains negligible.

\smallskip
\noindent\textbf{Client - Network Node Collusion.}
Unlike Sphinx, DSphinx intentionally replaces long-term node public keys with a secret-sharing architecture distributed among STTPs.
As a consequence, clients cannot independently compute node shared secrets.
If a client colludes with a node and learns its secret key, this restriction no longer applies for that node.
The client may then bypass the decentralized route sampling mechanism and force inclusion of the colluding node in arbitrary routes.
Alternatively, the client may replace legitimate hops with the colluding node after route generation.
Although this weakens route sampling guarantees, it does not compromise the secrets of honest nodes and therefore does not break the security of the entire network.

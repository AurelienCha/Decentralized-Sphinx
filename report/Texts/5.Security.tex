\section{Security Analysis}\label{sec:security}

This section outlines the security guarantees of our scheme.  
We first analyze the unlinkability and integrity forgery resistance in absence of collusion, and then discuss the effect of potential collusion with STTPs.


%%%%%%%%%%%%%%%%%
% UNLINKABILITY %
%%%%%%%%%%%%%%%%%

\subsection{Unlinkability}\label{sec:unlinkability}

To argue about sender-receiver unlinkability, we assume that an adversary cannot link a sender to its recipient without retracing the entire communication path.  
Thus, the problem reduces to proving unlinkability at the node level, meaning that an adversary cannot determine which outgoing packet corresponds to a given incoming packet.

We formalize unlinkability using a standard indistinguishability game between a challenger $\mathcal{C}$ and an adversary $\mathcal{A}$.  
Intuitively, the adversary observes a set of packets entering and leaving a node and attempts to determine which outgoing packet corresponds to a given incoming packet.

\medskip
\noindent\textbf{Game Definition:}
%
\begin{enumerate}
\item \textbf{Setup.}
  The challenger generates the node's secret keys and public system parameters $(G_1, \dots, G_n)$ as in the setup phase, ensuring all generators $G_j$ are independent and uniformly distributed elliptic curve points.
  Recall that generators are said to be independent if no participant knows any scalar relations among them.

  \item \textbf{Oracle.}  
  The adversary is granted access to an oracle, which on input of a nonce $x$ and routing path $\pi = (N_1, N_2, N_3, \Delta)$ outputs a valid header $(\alpha, \beta, \gamma)$ and its updated form $(\alpha', \beta', \gamma')$ after being processed by the node.

  \item \textbf{Challenge.}
  The adversary submits two distinct headers $(\alpha_0, \beta_0, \gamma_0)$ and $(\alpha_1, \beta_1, \gamma_1)$ that were not obtained during oracle queries.  
  The challenger selects a random bit $b_\mathcal{C} \in \{0,1\}$ and processes $(\alpha_{b_\mathcal{C}}, \beta_{b_\mathcal{C}}, \gamma_{b_\mathcal{C}})$ through the node, obtaining $(\alpha'_{b_\mathcal{C}}, \beta'_{b_\mathcal{C}}, \gamma'_{b_\mathcal{C}})$, which is then given to the adversary.

  \item \textbf{Guess.}
  The adversary outputs a bit ${b_\mathcal{A}} \in \{0,1\}$, attempting to guess which of the two input headers corresponds to the given output header.  
  The adversary wins if ${b_\mathcal{A}} = {b_\mathcal{C}}$.
\end{enumerate}

\noindent The adversary's advantage in breaking unlinkability is defined as
$$
\mathrm{Adv}^{\mathsf{unlink}}_{\mathcal{A}} = \big| \Pr[{b_\mathcal{A}} = {b_\mathcal{C}}] - \tfrac{1}{2} \big|.
$$
The scheme provides unlinkability if every probabilistic polynomial-time adversary achieves only a negligible 
advantage relative to the hardness of the underlying elliptic-curve assumptions (i.e. ECDLP on Curve25519).

\bigskip
\noindent\textbf{Proof Sketch:}
As in the original Sphinx construction, all packets have a fixed size (header and payload), preventing any adversary from correlating packets based on observable size patterns.
In addition, headers are computationally indistinguishable from random bitstrings, as empirically confirmed by the NIST randomness test suite (see Section~\ref{sec:NIST}).
Therefore, any successful distinguishing strategy by $\mathcal{A}$ must exploit a correlation between header's components $(\alpha, \beta, \gamma)$ and $(\alpha', \beta', \gamma')$.  
We analyze the possible cases below.

\medskip
\noindent{\textbf{Case 1: Linking via $\boldsymbol\alpha$.}}  
Network nodes reject packets with duplicate $\alpha$ values, preventing trivial replay-based linkage.  
The only relation between $\alpha$ and its processed form $\alpha'$ is $\alpha' = s \alpha$, where $s$ is the node's shared secret.  
If $\mathcal{A}$ can link headers via $\alpha$, it can compute $s$ such that $\alpha' = s \alpha$, thereby solving an instance of the Elliptic Curve Discrete Logarithm Problem (ECDLP).

\medskip
\noindent{\textbf{Case 2: Linking via $\boldsymbol\beta$.}}\label{sec:indep_generators}  
% \paragraph{\textbf{Security Note.}}\label{note:security_why_indep_generators}
% To preserve unlinkability, it is essential that the generators $ (\G{1}, \dots, \G{7}) $ are \textit{independent}, meaning their scalar relationships are unknown and computationally infeasible to derive.
% If the same generator \G{} were used across chunks (or their scalar relationships known), an adversary could compute chunk-wise difference between consecutive layers: $ \B{i}{j} - \B{i+1}{j} = \sG{i}{} $.
% Since the shared secret \s{i} remains consistent within a layer, the resulting differences would reveal a predictable pattern (uniform or preserved scalar relationships).
% This consistency could allow an adversary to correlate incoming and outgoing packets at a mixnode, thereby breaking the unlinkability property.
% Using independent generators for each chunk prevents such correlations and is therefore critical to the protocol's security.  
Each routing chunk $\beta_j$ and its corresponding processed value $\beta'_j$ satisfy:
$$
\beta_j - \beta'_j = s G_j, \quad \forall j \in \{1, \dots, n\}.
$$

To establish a link, $\mathcal{A}$ must either verify that the same shared secret $s$ is used among all chunks, or that a fixed scalar relationship is preserved between two generators $G_j$ and $G_{j'}$ (i.e. $z$ such that $G_j = z G_{j'}$).
Therefore, if generators are independent, then the adversary's task reduces to solving an instance of the ECDLP, either to recover $s$ or to determine $z$.

\medskip
\noindent{\textbf{Case 3: Linking via $\boldsymbol\gamma$.}}  
The integrity tag $\gamma$ is a weighted sum of the encrypted routing components:
$$
\gamma = s G + \sum_{j=1}^{n-2} h^{(j)}(s)\, \beta_j.
$$
Finding a correlation between $\gamma$ and $\gamma'$ without knowledge of $s$ or its derived weights $h^{(j)}(s)$ is no easier than linking via $\beta$ (Case 2).

\medskip
\noindent\textbf{Summary.}  
Under the hardness assumption of the ECDLP, and assuming independent generators, no probabilistic polynomial-time adversary $\mathcal{A}$ can achieve a non-negligible advantage in the unlinkability game.  
Therefore, we can conclude that the proposed scheme provides unlinkability.

\subsection{Integrity Forgery Resistance}\label{sec:integrity_forgery}

% A pseudorandom weighted checksum is used due to the decentralized nature of our scheme, which requires a homomorphic integrity mechanism.
% As a remainder, the integrity checksum is computed as:
% $$
% \C{i} = s_i G + \sum_j h^{(j)}(s_i)\, B_{(i,j)},
% $$
% where $B_{(i,j)}$ denotes the $j$-th header chunk, $s_i$ is the shared secret, and $h^{(j)}(s_i)$ is the $j$-th iterated hash of $s_i$.  
% This construction combines two elements: (i) a \emph{weighted sum}, and (ii) a blinding \emph{offset} term $s_i G$.  
% \newline

Integrity-forgery resistance requires that an adversary cannot produce a modified header that is accepted by an honest node.  
We formalize this property as a game in which the adversary attempts to forge a new header that passes integrity verification.

\newpage
\noindent\textbf{Game Definition:}
\begin{enumerate}
\item \textbf{Setup.}
  The challenger generates node's secret keys and public system parameters $(G_1, \dots, G_n)$ as in the setup phase, ensuring all generators $G_j$ are independent and uniformly distributed elliptic curve points.

  \item \textbf{Oracle.}  
  The adversary is granted access to an oracle, which outputs a valid header $(\alpha, \beta, \gamma)$.
  Then the adversary can change the $\beta$ values to $\beta'$.
  The adversary can then send the modified header $(\alpha, \beta', \gamma)$ to an oracle which will send the new integrity tag $\gamma'$.

  \item \textbf{Challenge.}
  The challenger submits a header $(\alpha, \beta, \gamma)$ with an $\alpha$ that has not been used during the oracle.
  The adversary modify chunks $\beta$ into $\beta_\mathcal{A}$, and update the integrity tag into $\gamma_\mathcal{A}$.

  \item \textbf{Guess.}
  The adversary wins if $\gamma_\mathcal{A} = \gamma_\mathcal{C}$, where $\gamma_\mathcal{C}$ is the integrity compute by the challenger on $\beta_\mathcal{A}$.
\end{enumerate}

\medskip
\noindent
The adversary's advantage in forging a valid integrity tag without knowing the shared secret is defined as
$$
\mathrm{Adv}^{\mathsf{forgery}}_{\mathcal{A}}(\lambda) = \big| \Pr[\gamma_\mathcal{A} = \gamma_\mathcal{C}] - \tfrac{1}{2^{\lambda}} \big|.
$$
Here, $\lambda$ denotes the bit-security of the underlying elliptic curve group (e.g. $\lambda = 128$ for Curve25519).
The scheme achieves integrity-forgery resistance if  $\mathrm{Adv}^{\mathsf{forgery}}_{\mathcal{A}}(\lambda)$  is negligible.
This means that the adversary cannot do better than randomly guessing the correct integrity tag.

\bigskip
\noindent\textbf{Proof Sketch:}
Each header chunk $\beta_{j}$ can be modified by an adversary in two possible ways: 
either (i) the chunk is replaced by a new point $\beta'_{j}$, or (ii) it is incremented by an elliptic curve point $P_j$.

\medskip
\noindent{\textbf{Case 1: Chunk Replacement.}}
Replacing $\beta_{j}$ with $\beta'_{j}$ requires updating the corresponding integrity $\gamma$ to $\gamma'$ such that:
$$
\gamma' = \gamma + h^{(j)}(\sHashed{})\, (\beta'_{j} - \beta_{j}).
$$
This operation necessitates knowledge of the weight $h^{(j)}(\sHashed{})$, which is derived from the hashed of the shared secret. 
Without this information, an adversary cannot produce a valid updated integrity tag.

\medskip
\noindent{\textbf{Case 2: Incremental Modification.}}
If the adversary only adds a point $P_j$ to a single chunk, the integrity tag must be updated as:
$$
\gamma' = \gamma + h^{(j)}(\sHashed{})\, P_j,
$$
which again requires knowledge of the corresponding weight $h^{(j)}(\sHashed{})$.

\medskip
\noindent{\textbf{Case 2.b: Balanced Increment.}}
A more sophisticated attempt consists in modifying two chunks, say $j$ and $j'$, to preserve the checksum balance:
$$
\gamma' = \gamma + h^{(j)}(\sHashed{})\, P_j + h^{(j')}(\sHashed{})\, P_{j'}
$$
If the adversary knows a scalar $z$ such that $h^{(j)}(\sHashed{}) = z\,h^{(j')}(\sHashed{})$,  it becomes:
$$
\gamma' = \gamma + h^{(j')}(\sHashed{})\, (z P_j + P_{j'})
$$
Thus, the adversary can choose any $P_j$ and set $P_{j'} = -z P_j$, keeping $\gamma' = \gamma$ unchanged and thereby forging integrity.  

\medskip
\noindent\textbf{Summary.}
Successful integrity forgery requires at least knowledge of scalar relations between the weights $h^{(j)}(\sHashed{})$.  
Since these weights are derived from one-time shared secrets through iterated hashing, such relations are computationally infeasible in the absence of collusion.

\medskip
\noindent\textbf{Remarks.}
\label{replay_resistance}\label{wrap_resistance}
The original Sphinx article~\cite{sphinx} takes \emph{replay resistance}
and \emph{wrap resistance} into account.
\emph{Wrap resistance} means an adversary must not be able to transform a header $(\alpha, \beta, \gamma)$ into a new valid header $(\alpha', \beta', \gamma')$ such that, after being decrypted by a node, the packet becomes $(\alpha, \beta, \gamma)$ again.  
\emph{Replay resistance} is inherited from the original Sphinx construction since the nodes maintain a table of previously seen $\alpha$ values and discard replayed values (with tables reset only when keys are updated).
Thus, if an adversary want to replay a packet, he would need to alter $\alpha$ (and consequently $\beta$) while still producing a consistent integrity tag $\gamma$. % which directly reduces to the problem of forging integrity.  
Similarly, \emph{wrap resistance} also requires producing a modified header that passes integrity verification.
Hence, \emph{replay resistance} and \emph{wrap resistance} reduce to \emph{integrity forgery resistance}.

\subsection{Collusion Analysis}\label{sec:collusion}

The preceding security arguments assume an ideal setting without collusion.
However, since our construction relies on semi-trusted third parties (STTPs), it is essential to assess the system's resilience to collusion. 
In this section, we formalize potential collusion scenarios and evaluate the additional capabilities an adversary may gain when colluding with subsets of STTPs.

\medskip
\noindent{\textbf{STTP Advantages.}}
Among the set of $T$ semi-trusted third parties used to build an header, an STTP $t$ reveals three types of information:  
\begin{itemize}
  \item an additive share of destinations $N_{(i,t)}$, such that\newline 
  $N_i = \sum_{t=1}^T N_{(i,t)}$;  
  \item an additive share of shared secrets $s_{(i,t)}$, such that\newline 
  $s_i = \sum_{t=1}^T s_{(i,t)}$;
  \item the hash values of the full shared secrets $\{h(s_1), h(s_2), h(s_3)\}$.
\end{itemize}
%
Since the first two items are additive shares, they provide no information unless all $T$ shares are collected.
Hence, as long as at least one of the $T$ STTP remains honest, neither destinations nor shared secrets can be reconstructed.
The only additional information available to an adversary colluding with an STTP is the set of hash values $h(s_i)$, which determine the weights used in the checksum integrity tags for all the nodes in the path.  
However, the integrity's blinding offset $s_i G$ prevents trivially associating weights to specific packets.
Without this association, the adversary can only attempt modifications on a random packet, succeeding with probability $1/n$ among $n$ packets in the entire network.

\medskip
\noindent\textbf{Case of Corrupted Node.}  
While an STTP alone reveals only unlinked integrity weights, when colluding with a corrupted node, it enables the adversary to \emph{associate those weights to a specific packets} observed at the corrupted node.  
Concretely, a corrupted node computes its shared secret $s_i$ using the packet's cryptographic element $\alpha$, derive $h(s_i)$, and compare it against the set of weights disclosed by the colluding STTP.
If the compromised STTP participated in the construction of this packet's header, a match occurs, allowing the adversary to recover the remaining weights associated to this packet across all the nodes in its path.

In addition to revealing the node's position along the path, associating these weights to a packet grants the adversary several further capabilities:
\begin{enumerate}
  \item \textbf{Integrity Forgery.} The adversary can modify any header chunks (including the destination $\Delta$) and recompute valid integrity tags, as discussed in Section~\ref{sec:integrity_forgery}.
  \item \textbf{Weaker Unlinkability.} The adversary may attempt to trace a packet by modifying it, updating the integrity tag, and checking if it succeeds subsequent integrity verifications.
  This succeeds with probability $1/n$ and fails with probability $(n-1)/n$, where $n$ is the node's batch size.%\todo{this also is wrong, see comment below}
  %The probability of a corrupted node capturing a  specific message depends on the routing algorithm of the network. For example in a free-routing network, the probability of an adversary succeeding is $1/n$ where $n$ is the total number of messages. However in modern decentralized networks routing algorithms are more complex and takes into consideration many parameters such as geolocation, trust and bandwidth of the servers~\cite{rahimi2023larmix}. 
\end{enumerate}

\medskip
\noindent\textbf{Summary.}
Collusion with either STTPs or network nodes alone does not compromise security.
STTPs reveal only additive shares and unlinked weights, while nodes reveal only shared secrets.  
However, when colluding simultaneously with both STTP and a network node, an adversary can correlate integrity weights with specific packets, thereby allowing integrity forgeries.  
Unlinkability remains computationally hard to break, but the adversary may probabilistically test packets with success probability $1/n$, where $n$ is the node's batch size. 
In the worst case scenario, namely collusion between the STTP and both the entry and exit nodes, the anonymity of the communication breaks down, allowing the sender and receiver to be linked.
In summary, the security against collusion rests on the following minimal assumptions:
(i) at least one STTP remains honest;
(ii) at least one node on the path is not compromised; and
(iii) adversaries cannot simultaneously collude with both a STTP and a node (in particular, when entry and exit nodes are corrupted).
Under these conditions, collusion yields at most negligible advantage beyond trivial guessing.

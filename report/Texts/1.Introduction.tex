
\section{Introduction}

The Sphinx packet format, introduced by Danezis and Goldberg~\cite{sphinx} in 2009, has become a foundational component of modern anonymous communication systems.  
It is used in decentralized infrastructures such as the Lightning Network~\cite{poon2016bitcoin}, as well as mixnet-based systems including Nym~\cite{nym-network-whitepaper} and Katzenpost~\cite{infeld2025echomix}.

In these networks, messages traverse multiple nodes, where each intermediary decrypts and forwards packets to the next entity in the path. 
The message content is protected through layered encryption in the Sphinx payload, and the routing information is similarly layered and encrypted within the Sphinx header. With this packet format, an adversary cannot correlate an input message with an output message based on packet structure or size. 
Additionally, an intermediary node along the message path does not learn its position within the route; it can infer only the immediately preceding and succeeding nodes, not the entire path. 
Sphinx achieves this through a compact packet structure that offers cryptographically robust unlinkability as well as per-hop integrity protection.

However, despite its strengths, the Sphinx packet format is fully constructed \emph{centrally} by the clients before entering the network which makes the system vulnerable to various attacks. 
For example, a client may bias route selection by violating the routing algorithm, thereby reducing the number of messages mixed at a specific node in order to target an honest client or degrade the system's overall anonymity~\cite{benguirat2022mixnet}. 
An adversary may also mount an (N-1) attack~\cite{raymond2001traffic} by dropping all but one message and forwarding only its own traffic to a chosen node, again violating the routing algorithm. Additionally, enforcing exit policies has long been a serious challenge in any decentralized network~\cite{oram2001peer, dingledine2001free}, particularly when network privacy is the main goal. 
On one hand, clients should not be linked to their final destinations. 
On the other hand, the system must prevent unauthorized or abusive traffic. 
We therefore argue that decentralizing Sphinx header construction is crucial in achieving more robust, verifiable, and flexible anonymous communication systems and decentralized networks.

In this work, we introduce DSphinx, a \emph{decentralized Sphinx header
construction} that distributes the computation across multiple independent
semi-trusted third parties (STTPs).  To the best of our knowledge, this is
the first work to decentralize the Sphinx packet format.

In this work, we introduce DSphinx, a \emph{decentralized Sphinx header construction} that distributes the computation across multiple independent semi-trusted third parties (STTPs).
Achieving decentralization while maintaining Sphinx's cryptographic guarantees raises several challenges.  
First, the protocol must prevent individual STTP, or any coalition of corrupted STTPs, from learning routing information or recovering cryptographic secrets.  
Second, intermediary nodes (i.e mixnodes or peers) should learn no more than in the traditional Sphinx design.
Each node must reveal only its own shared secret and the address of the next node, but nothing about the rest of the route.  
Third, unlinkability must be preserved even against a powerful passive adversary capable of observing all traffic inputs and outputs and performing sophisticated cryptanalytic analysis. 
Finally, distributing the computation must not introduce any trapdoor, bias, or structural weakness that an adversary could exploit to correlate packets or manipulate header values.

Our construction addresses these challenges by encoding routing information as elliptic curve points, splitting secrets via additive secret sharing, and using a homomorphic pseudorandom weighted checksum as an integrity mechanism that remains compatible with decentralized computation.
To the best of our knowledge, this is the first work to decentralize the Sphinx packet format. 
We emphasize, however, that while DSphinx preserves Sphinx's security properties, it does not on its own prevent attacks related to client-side path selection. 
Yet, our
decentralized header construction is an essential step towards robust,
verifiable and flexible decentralized networks, enabling distributed
path selection and key derivation, or the efficient enforcement of exit
policies.

\noindent In summary, our main contributions are as follows:
\begin{itemize}
    \item We design \emph{DSphinx}, the first \emph{decentralized Sphinx
header construction}, that enables clients to distribute header computation while preserving the anonymity and cryptographic guarantees of the original Sphinx design;
    \item We provide a detailed security analysis of \emph{DSphinx},
considering passive and active network adversaries, corrupted mixnodes, and colluding STTPs;
    \item We provide a Python implementation of our header construction,
which we will release under an open-source license;\footnote{Our DSphinx
implementation is available for review: \url{\artifact}}
    \item Using the NIST SP-800-22 randomness test suite, we empirically demonstrate that the resulting headers are at least as indistinguishable from random bitstrings as the original Sphinx. In fact, DSphinx successfully passes 3 out of 15 additional randomness tests.
    \newline
\end{itemize}
